> 日期：2026-06-20
> 分析对象：`backends/local/kernel_modules/snvme-5.10-npu/`
> 参考基准：
> - 原始 snvme：`backends/local/kernel_modules/snvme-5.15.0-public/`（基于 5.15、依赖 NVIDIA GPUDirect）
> - 目标内核原生驱动：`kernel-openEuler-22.03-LTS-drivers-nvme/drivers/nvme/host/`（openEuler 22.03-LTS，5.10 内核）

## 〇、结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| **能否在 5.10 编译？** | ✅ **静态审查认为可以编译通过**。所有真正 5.15-only 的内核符号都已用 `#if LINUX_VERSION_CODE < KERNEL_VERSION(5,15,0)` 隔离，5.10 分支实现与 openEuler 原生 nvme 写法一致；x86_64 专属头已换成架构中立头。**但本机无 5.10/aarch64 环境，无法实测编译，需在昇腾服务器上验证。** |
| **NVIDIA 函数怎么替换的？** | ⚠️ **没有接入任何昇腾 NPU API，也没有实现 P2P DMA**。替换只做了两件事：(1) 补一个 `nv-p2p.h` 桩头让代码能编译；(2) 把模块加载时"找不到 NVIDIA 符号就失败"改成"打警告继续，进入 HOST-ONLY 模式"。GPU/显存数据通路是**空桩占位**，运行时靠原生的"找不到符号返回 `-ENOMEM`"机制自动失效。 |
| **snvme_smoke.c 能否通过？** | ✅ **理论上能通过**。该测试**纯主机内存 + 内核态 + NVMe SSD，完全不碰 GPU/NPU 显存**。前提：两个 .ko 能加载 + 有一块 NVMe SSD。唯一架构隐患是 ARM64 上 `mmio_read64` 的非对齐 64 位 MMIO 访问。 |
| **`--gpu` 路径（snvme_smoke_gpu.cu）？** | ❌ **必然失败/被跳过**。它是 CUDA 代码，昇腾上无 `nvcc` 会被 Makefile 跳过，且硬依赖 NVIDIA 显存，尚未迁移到 Ascend C。第一阶段不测它。 |

**一句话**：第一阶段目标（5.10 内核移植 + 让模块在无 NVIDIA 的昇腾机上能加载、跑通纯主机内存的 `snvme_smoke.c`）是**自洽且可达成的**；但"NPU 显存直连（GPUDirect 等价物）"**尚未实现**，仍是 TODO。

## 一、背景与架构前提（理解后面所有结论的关键）

### 1.1 snvme 是树外（out-of-tree）独立驱动，不是给内核打补丁

- snvme 通过 `#include "nvme.h"` 引入的是**自带的私有 `nvme.h`**，里面所有结构体/函数都改名为 `snvme_*`（如 `snvme_alloc_request`、`snvme_setup_cmd`、`snvme_complete_rq`、`__snvme_submit_sync_cmd`）。
- 构建产物是 `snvme-core.ko` + `snvme.ko`，与内核自带的 `nvme.ko` **完全独立、互不干扰**。设备节点也刻意区分：`/dev/ssnvme<N>`、磁盘命名 `snvme%dn%d`（区别于 in-tree 的 `/dev/nvme*`）。

**这一点直接决定了兼容性风险的边界**：
- snvme 私有结构体里的字段差异（`struct nvme_ctrl/nvme_ns/nvme_ns_head`）**永远不会与内核原生 nvme.h 冲突**，因为树外模块根本不包含内核那份 `drivers/nvme/host/nvme.h`。
- 真正的版本兼容性风险**只剩一处**：snvme 调用**真正的内核导出符号**（block 层、PCI、DMA、genhd 等）的地方——这些 5.10 与 5.15 签名/存在性不同，必须条件编译。

### 1.2 两类改动要分清

`snvme-5.10-npu` 相对 `snvme-5.15.0-public` 的改动，本质是**两条独立主线叠加**：

1. **内核版本移植（5.15 → 5.10）**：占绝大多数，与 NPU 无关。用 `#if LINUX_VERSION_CODE < KERNEL_VERSION(5,15,0)` 条件编译，`<5.15` 分支是为 openEuler 5.10 新增的写法，`#else` 保留原始 5.15 写法。
2. **GPU → NPU 适配（NVIDIA → 昇腾）**：实际改动**极少**，标记为 `[SNVME-NPU 迁移修改 #N]`。
3. **架构适配（x86_64 → aarch64）**：个别地方（如 x86 专属头），标记为 `batch7` 等。

迁移标记统计（`grep -c "SNVME-NPU\|LINUX_VERSION_CODE"`）：
`core.c:25`、`pci.c:11`、`multipath.c:9`、`ioctl.c:5`、`map.c:2`、`nv-p2p.h:2`、`nvfs-p2p.h:1`。

## 二、内核版本问题：5.10 vs 5.15 API 差异及适配情况

下表是 snvme 实际调用到的、且 5.10 与 5.15 不同的**真实内核符号**。每一处都已在 `.c` 文件中条件编译适配，5.10 分支写法与 openEuler 原生 nvme 驱动一致。

### 2.1 block 层 / request 执行 API

| API | 5.10 原生写法 | 5.15 写法 | npu 适配位置 |
|---|---|---|---|
| `blk_execute_rq` | `blk_execute_rq(q, disk, rq, at_head)`，4 参、返回 **void**，状态从 `nvme_req(rq)->status` 读 | `blk_execute_rq(disk, rq, at_head)`，返回 `blk_status_t` | ✅ core.c `nvme_execute_rq()` ~L1107 |
| `blk_execute_rq_nowait` | 多一个首参 `request_queue *q` | `blk_execute_rq_nowait(NULL, rq, ...)` | ✅ core.c keep-alive ~L1360；pci.c abort ~L1567、delete-queue ~L2886 |
| `blk_mq_set_request_complete()`（5.13+） | 内联 `WRITE_ONCE(req->state, MQ_RQ_COMPLETE)` | 直接调辅助函数 | ✅ core.c `nvme_host_path_error()` ~L407 |
| `bvec_virt()`（5.15+） | `page_address(req->special_vec.bv_page) + req->special_vec.bv_offset` | `bvec_virt(&req->special_vec)` | ✅ core.c `snvme_cleanup_cmd()` ~L1022 |

> 说明：`timeout` 回调返回类型三方都是 `enum blk_eh_timer_return`（**不是** `blk_status_t`），`queue_rq`/`init_request`/`poll` 签名 5.10 与 5.15 一致，无需适配。

### 2.2 genhd / gendisk 生命周期

| API | 5.10 原生 | 5.15 | npu 适配位置 |
|---|---|---|---|
| `device_add_disk` | 返回 **void**（判错版叫 `device_add_disk_safe`） | 返回 **int** | ✅ core.c `nvme_alloc_ns()` ~L4057，5.10 分支不判返回值，用 `if(0) goto` 保留标签可达 |
| `blk_alloc_disk()`（5.14+） | **无**，用 `blk_alloc_queue()` + `alloc_disk(0)` + 手工挂 `disk->queue` | `blk_alloc_disk(numa_node)` | ✅ multipath.c `nvme_mpath_alloc_disk()` ~L480 |
| `disk_live()`（5.15+） | `disk->flags & GENHD_FL_UP` | `disk_live(disk)` | ✅ core.c `nvme_first_scan()` ~L1983 |
| `disk_update_readahead()`（5.15+） | `blk_queue_update_readahead(disk->queue)` | `disk_update_readahead(disk)` | ✅ core.c `nvme_update_ns_info()` ~L2064 |
| `set_capacity_and_notify()`（5.12+） | `set_capacity_revalidate_and_notify(disk, size, false)` | `set_capacity_and_notify(disk, size)` | ✅ core.c ~L139、~L1958 |
| `blk_mq_alloc_disk` / `blk_cleanup_disk` | **openEuler 5.10 已回移植（backport）**，原生 core.c 在用 | 有 | ✅ 直接用，安全 |

### 2.3 struct bio / 磁盘关联（5.14 的 `bi_disk`→`bi_bdev` 大改名）

5.14 把 `bio->bi_disk`/`bi_partno` 合并成 `bi_bdev`，并引入 `bio_set_dev()`；`gendisk->part0` 从内嵌 `struct hd_struct` 变成 `struct block_device *`。

| 场景 | 5.10 原生写法 | 5.15 写法 | npu 适配位置 |
|---|---|---|---|
| bio 关联磁盘 | `bio->bi_disk = disk`（`gendisk*`） | `bio_set_dev(bio, disk->part0)` | ✅ multipath.c ~L90/L325/L346；ioctl.c `nvme_submit_user_cmd()` ~L65/L94 |
| 取 head | `bio->bi_disk->private_data` | `bio->bi_bdev->bd_disk->private_data` | ✅ multipath.c ~L325 |
| `trace_block_bio_remap` | 多一个首参 `request_queue*` | 无该首参 | ✅ multipath.c ~L346 |
| `part0` 类型 | 内嵌 `hd_struct`，用 `gendisk*` 替代 | `block_device*` | ✅ ioctl.c ~L65 |

### 2.4 struct nvme_ctrl 字段 / NVM 命令集

| 点 | 5.10 原生 | 5.15 | npu 适配位置 |
|---|---|---|---|
| `ctrl->max_zeroes_sectors` | **字段不存在** | 有 | ✅ core.c ~L1967，5.10 分支 write-zeroes 上限置 0 |
| `struct nvme_id_ctrl_nvm`（NVM 命令集 Identify CNS=0x06） | **内核头不存在** | 有 | ✅ core.c `nvme_init_non_mdts_limits()` ~L2981，5.10 分支跳过 NVM identify，仅按 `oncs & DSM` 设 discard 上限；`_nvme_check_size()` 的 `BUILD_BUG_ON` 也仅 5.15 编译 |

### 2.5 模块参数 / 驱动绑定（openEuler 特有的"未导出符号"问题）

| API | 问题 | npu 5.10 方案 |
|---|---|---|
| `param_set_uint_minmax` | openEuler 5.10 **未导出** | ✅ pci.c `io_queue_depth_set()` ~L261，手动 `kstrtou32` + 范围校验 + `param_set_uint` |
| `device_driver_attach` | openEuler 5.10 **未导出**（mainline v5.5+ 有，但该内核裁掉了，补 extern 也 modpost 链接失败） | ✅ pci.c `snvm_bind_driver()` ~L6327，改用 `pci_dev->driver_override = "snvme"`（`struct pci_dev` 自 v3.16 起就有的字段）锁定只认 snvme，再调已导出的 `device_attach()` 触发 probe |

> `device_driver_attach` 这处尤其关键：不能用裸 `device_attach()`（会挑任一匹配驱动，可能误绑回内核 stock nvme），用 `driver_override` 钉死才安全。

### 2.6 私有 nvme.h 的处理策略（一个需要写进文档的注意点）

⚠️ `snvme-5.10-npu/nvme.h` 与 `snvme-5.15.0-public/nvme.h` **字节级完全相同**，且**不含任何 `LINUX_VERSION_CODE` 保护**。

- 这**不会**导致编译失败——它是 snvme 私有头，所有 5.15 字段都在私有结构内，树外编译不与内核冲突。
- 但意味着移植者**有意只改 .c 不改 .h**，依赖"私有结构自洽 + .c 里条件编译调用内核符号"这一策略。该策略成立，但后续维护者需明确知道 `nvme.h` 并非"已按 5.10 改过"，避免误判。

### 2.7 版本适配总体评估

- **编译/链接层面：无阻塞性问题**。所有 5.15-only 内核符号（`set_capacity_and_notify`、`disk_update_readahead`、`blk_alloc_disk`、`bvec_virt`、3参版 `blk_execute_rq`）都被 `#if<5.15` 隔离，5.10 上不会编译到。两个"较新但 openEuler 已 backport"的符号（`blk_mq_alloc_disk`/`blk_cleanup_disk`）在 5.10 树中确实存在。**未发现会导致链接失败的裸调用。**
- **一处功能弱化（非编译错误）**：`device_add_disk` 那处 5.10 用 `if(0)` 跳过错误检查（原生用 `device_add_disk_safe` 判错），加盘失败路径不会被捕获，运行期健壮性略降。建议记录，后续可考虑改用 `device_add_disk_safe`（若 openEuler 5.10 有导出）。

## 三、NVIDIA → 昇腾 NPU：替换是怎么做的（核心关切）

### 3.1 最关键的事实

**第一阶段的迁移没有引入任何真正的昇腾 NPU API，也没有实现 peer-to-peer DMA。** 针对 NVIDIA 的"替换"本质只有两类：

1. **让模块在没有 NVIDIA 驱动的机器上"能编译 + 能加载"**——补桩头 + 把硬失败改软警告。
2. **GPU/显存数据通路代码一行没改**——靠原生的"找不到符号返回 `-ENOMEM`"机制在运行时自动失效。

### 3.2 文件改动总览

| 文件 | 状态 | 性质 |
|---|---|---|
| `nv-p2p.h` | **NPU 新增**（原始目录没有此文件） | 桩头，纯编译期 |
| `pci.c` `nvme_init()` | DIFF（迁移修改 #1） | **唯一实质功能改动**：硬失败 → 软警告 HOST-ONLY |
| `nvfs-p2p.c` | **字节完全相同** | 原生符号动态查找包装，未改 |
| `nvfs-pci.c/.h`、`nvfs-core.h` | **字节完全相同** | PCIe 拓扑助手（link speed/width），与 GPU 显存无关 |
| `nvfs-p2p.h` | DIFF | 仅加一行 `struct pci_dev;` 前置声明（5.10 编译修复） |
| `map.c`/`map.h` | DIFF | 仅格式化 + 中文注释，**GPU 路径逻辑零改动** |

### 3.3 逐项替换分析

#### 替换 ① `nv-p2p.h`：缺失头文件 → 最小桩头（空桩，仅为编译）

- **原始**：依赖机器上装的 NVIDIA GPU 驱动提供 `nv-p2p.h`（定义 `struct nvidia_p2p_page_table`、`struct nvidia_p2p_dma_mapping`）。原始 snvme 目录里**根本没有这个文件**。
- **NPU**：新增桩头，只给出 snvme 编译期真正访问的两个字段：`nvidia_p2p_page_table { u32 entries; }`、`nvidia_p2p_dma_mapping { u64 *dma_addresses; }`。还套了一层 `#ifndef _NV_P2P_H_` 双向防护，避免机器上同时存在真 NVIDIA 头时 `redefinition` 冲突。
- **影响**：**纯空桩占位**。host-only 运行时根本走不到读这些字段的代码（`nvfs_nvidia_p2p_get_pages()` 在无 NVIDIA 时先返回 `-ENOMEM` 提前退出）。缺它会 `fatal error: nv-p2p.h: No such file`。

#### 替换 ② `pci.c` `nvme_init()`：硬失败 `-EOPNOTSUPP` → 软警告 HOST-ONLY（**唯一真实功能改动**）

```c
// 原始（5.15）：找不到 nvidia_p2p_* 符号 → 整个模块加载失败
if (nvfs_nvidia_p2p_init()) {
    printk("Could not load nvidia_p2p* symbols\n");
    ret = -EOPNOTSUPP;
    return ret;
}
// NPU 改成：打警告，继续加载进入 HOST-ONLY 模式
if (nvfs_nvidia_p2p_init()) {
    printk(KERN_WARNING "snvme: nvidia_p2p* symbols not found; running in HOST-ONLY mode ...");
    /* 不再 return */
}
```

- **影响**：**真实修复**。让模块在无 NVIDIA 的昇腾机上能成功 `insmod`。host 内存路径照常工作；device-memory ioctl 由下游 `nvfs` 包装返回 `-ENOMEM/-EOPNOTSUPP`，不会 oops。`nvme_exit` 仍调 `nvfs_nvidia_p2p_exit()`，内部对 NULL 判空，安全。

#### 替换 ③ `map.c` GPU 路径：完全未改（空桩，靠下游 `-ENOMEM` 失效）

- `map_gpu_memory()` / `map_gpu_ioqueue_memory()` 仍调 `nvfs_nvidia_p2p_get_pages/dma_map_pages/...`，**逐字节等价**（diff 全是指针风格 + 中文注释）。
- **影响**：**纯空桩占位**。运行时因 NVIDIA 符号未加载返回 `-ENOMEM`，`map_gpu_memory` 提前报错退出，**走不通 P2P DMA**。注释明说："NPU 迁移就是把这两个 nvfs 调用换成昇腾 HBM 的 pin/map 能力……第一阶段只用 host 路径"——昇腾 API **尚未接入，是 TODO**。

#### 替换 ④ `map.c` host 路径：真实现（与 NVIDIA 无关）

- host 路径用**标准内核 API** `get_user_pages` + `dma_map_page`（`map_user_pages()`），把用户页 pin 住、过 IOMMU 拿到 NVMe 可用的总线地址。两版逻辑等价（仅加注释）。这是第一阶段测试**唯一依赖、且能跑通**的通路。

#### 替换 ⑤ `nvfs-p2p.h`：加 `struct pci_dev;` 前置声明（5.10 编译修复）

- openEuler 5.10 的 `module.h` 包含链不同，到本头时 `struct pci_dev` 尚未声明，触发 C "函数原型作用域幽灵类型" → `conflicting types`。加一行前置声明修复。纯编译期，不改逻辑。

### 3.4 "真实现" vs "空桩占位" 速查表

| 功能通路 | 状态 | 说明 |
|---|---|---|
| 模块加载（无 NVIDIA 时） | ✅ 真实现 | `nvme_init` 软失败（替换 ②） |
| host 内存映射 `NVM_MAP_HOST_MEMORY` | ✅ 真实现 | 标准 `get_user_pages`+`dma_map_page` |
| 编译通过（缺头/类型冲突） | ✅ 真实现 | `nv-p2p.h` 桩头 + `struct pci_dev;` 前置声明 |
| GPU/device 显存映射 `NVM_MAP_DEVICE_MEMORY` | ❌ 空桩占位 | `map.c` 逻辑未改，运行时 `-ENOMEM` |
| GPU IO 队列显存 | ❌ 空桩占位 | 同上 |
| **昇腾 NPU peer-DMA / HBM pin&map** | ❌ **完全未实现** | 所有"昇腾/华为/HBM"字样都在注释里，是 TODO，无任何昇腾 API 调用 |

> 补充：`core.c` 里的 `NVME_F_PCI_P2PDMA`/`QUEUE_FLAG_PCI_P2PDMA` 是**内核原生 PCIe P2PDMA 标志**，与 NVIDIA GPUDirect 无关，未改动。

## 四、snvme_smoke.c 测试能否通过

### 4.1 测试是什么

`snvme_smoke.c` 是**端到端 UAPI 健全性测试**，自包含、**只链接 libc**（no CUDA、no libnvm），只含一个 UAPI 头 `ioctl.h`（位于 `backends/local/nvme/libnvm/include/ioctl.h`）。它逐一走通"用户态 ↔ snvme 内核模块"的每个入口。

两种模式：
- **默认 UAPI-smoke 模式**（安全）：不触发 NVMe 控制器 probe、不碰数据通路。
- **`--bind` full bring-up 模式**（破坏性）：真正接管控制器，做一次 512B `pread`，再拆除。

### 4.2 测试流程（默认模式，全部纯主机内存 + 内核态）

| 步骤 | 操作 | 验证 |
|---|---|---|
| [1] | `open("/dev/snvm_control")` | 核心模块已加载 |
| [2] | `SNVM_CHRDEV_CREATE(BDF)` | 为该卡创建 per-controller 字符设备、回写 minor |
| [3] | `open("/dev/ssnvme<minor>")` | per-controller 节点可用 |
| [4] | `mmap(BAR0, 8KiB)` | BAR0 寄存器空间能映射进用户态 |
| [5] | 读 CAP 寄存器 | BAR0 确实映射到真实寄存器 |
| [6] | `NVM_SET_IOQ_NUM` | 队列预算状态机（ioq_num=2、`F_ON_HOST`、cap=32） |
| [7][8] | `mmap` 一页 + `NVM_MAP_HOST_MEMORY`(SQ/CQ) | 把**主机页** pin 住映射为 0 号队列 SQ/CQ 环 |
| [9] | `NVM_SET_SHARE_REG(1)` | `use_sreg` 门控 |
| [F1–F3] | UNMAP + CLEAR_IOQ + munmap + close + CHRDEV_REMOVE | 状态机干净复位、minor 回收 |

`--bind` 段额外：`SNVM_DEVICE_BIND` → 轮询 `NVM_GET_DEV_INFO`（~10s 等 probe）→ `open("/dev/<disk_name>")` + `pread(512)` → `SNVM_DEVICE_UNBIND`。

### 4.3 是否依赖 GPU/NPU 显存？——**完全不依赖**

- 头部注释明确："no CUDA, no libnvm ... links against nothing but libc"。
- 步骤 [7][8] 队列环用**普通主机内存**：`mmap(MAP_PRIVATE|MAP_ANONYMOUS)` + `NVM_MAP_HOST_MEMORY` + `flags=NVM_QUEUE_SETUP_F_ON_HOST`。
- 无任何 `cudaMalloc`/`NVM_MAP_DEVICE_MEMORY`/`aclrtMalloc`。

> GPU 依赖在**另一个文件** `snvme_smoke_gpu.cu`（CUDA，`cudaMalloc` + `NVM_MAP_DEVICE_MEMORY`，需 NVIDIA 驱动 + `nvfs_nvidia_p2p_init`）。它含大量"NPU 迁移提示"注释（`cudaMalloc`→`aclrtMalloc` 等），是**后续迁移目标，目前仍是 CUDA**。

### 4.4 在昇腾服务器（有 NPU、无 NVIDIA GPU）上的通过/失败预测

**前提**：两个 .ko 已编译并 `insmod`、`/dev/snvm_control` 存在、有一块 NVMe SSD（root 权限）。

**会通过：**
- `snvme_smoke.c` 默认 UAPI-smoke 模式 [1]–[9]、[F1]–[F3]：**全部可通过**（纯主机内存 + 内核态）。
- `--bind` 模式 [B1]–[B4]：**可通过**（有真实 NVMe SSD 且允许 snvme 破坏性接管）。

**架构相关风险点（源于 ARM64，非缺 GPU）：**
- ⚠️ **步骤 [4]/[5] `mmio_read64`**：源码注释说"x86 支持非对齐 64 位 MMIO load；移植到不支持的架构要改成两次 readl"。**昇腾是 ARM64，对设备内存的非对齐 64 位访问可能产生对齐异常/总线错误。这是潜在失败点**，建议迁移时改成两次 `readl` 拼接。
- 步骤 [5] 读 CAP：若控制器在 D3/掉电，CAP 读回 `0xFFFF...` 只告警继续（不算失败）；读回全 0 → `step_fail` EIO。取决于 NVMe 上电状态。

**会失败/被跳过：**
- ❌ `--gpu`（`snvme_smoke_gpu`）：昇腾无 `nvcc`，Makefile `ifeq($(HAVE_NVCC),yes)` 跳过编译，脚本发现二进制不存在 → 报 "not built" 退出。即便强行编译，运行期也会因 `cuInit` 在无 NVIDIA 卡上失败。**第一阶段不要加 `--gpu`。**

### 4.5 运行前置条件

- 加载 `snvme-core.ko` + `snvme.ko`（脚本检测 `/dev/snvm_control`）。
- root 权限（`sudo`）。
- 一块真实 NVMe SSD，PCI BDF 通过参数 / `$PCI_ADDR` / `lspci -D -d ::0108` 自动取。
- 编译：`snvme_smoke.c` 只需 `cc`；`snvme_smoke_gpu` 需 `nvcc`（无则 Makefile 自动跳过）。
