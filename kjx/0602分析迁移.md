# GeminiFS 迁移到华为 NPU 910C：Kernel Modules 排查与 AIV 对接分析

> 日期：2026-06-02  
> 仓库：`GPU-Companion-File-System/Geminifs`  
> 当前分支：`refactor/code-cleanup`  
> 当前提交：`1c4b34c9f25fbde2bd2f0380e1928d4867bf0f05`

## 1. 结论先行

你的判断基本正确：迁移 GeminiFS 到华为 NPU 910C 时，第一阶段应当先聚焦
`backends/local/kernel_modules/` 下的 SNVMe 内核模块及其独立测试，而不是一开始
就运行完整 GeminiFS。

但不能简单地把 `snvme-5.15.0-public` 拷到华为服务器直接跑全部测试，原因有两个：

1. **内核 baseline 必须匹配华为服务器实际运行的内核。** 当前仓库只维护了
   `snvme-5.15.0-public` 和 `snvme-5.4.241-1-tlinux4-0017` 两个 baseline。
   如果华为服务器的 `uname -r` 不是对应前缀，需要先新增
   `snvme-<华为内核版本>` 目录并完成 NVMe 驱动 uplift。
2. **当前 SNVMe 是 NVIDIA/CUDA 专用实现，不是通用加速器实现。**
   `snvme.ko` 加载时会动态查找 `nvidia_p2p_*` 符号；GPU 测试还依赖
   `cudaMalloc`、`cudaHostRegister(..., cudaHostRegisterIoMemory)`、
   `cudaHostGetDevicePointer` 和 `__threadfence_system()`。仅有华为 NPU 的服务器
   上，原始模块大概率在 `insmod snvme.ko` 阶段就会因为找不到 NVIDIA 符号失败。

因此，正确方向是把问题拆成两条相对独立的迁移线：

- **Linux 内核版本迁移线**：SNVMe fork 是否能在华为服务器内核上编译、加载、绑定
  NVMe，并完成纯 CPU 队列和 BAR0 映射测试。
- **NVIDIA GPU Direct 替换线**：华为驱动/CANN/AIV 是否提供足够能力，让 NVMe
  直接 DMA 到 NPU 内存，并让 AIV 核直接写 NVMe BAR0 doorbell。

后者才是需要和华为 AIV、驱动部门重点对接的部分。它不是单一的“doorbell 注册
权限”问题，而是一组跨内核驱动、IOMMU、PCIe 拓扑和 AIV 指令语义的问题。

## 2. 当前仓库里的相关组成

### 2.1 SNVMe kernel module

目录：

```text
backends/local/kernel_modules/
├── PORTING.md
├── snvme-5.15.0-public/
├── snvme-5.4.241-1-tlinux4-0017/
└── test/
```

SNVMe 是 Linux in-tree NVMe host driver 的 fork。它保留普通块设备能力，同时允许
用户态或加速器核直接拥有 NVMe SQ/CQ：

- `/dev/snvm_control`：控制字符设备，用于 NVMe PCI 设备 bind/unbind 和创建
  per-controller 字符设备。
- `/dev/ssnvme<N>`：用于 queue ioctl 和 BAR0 `mmap()`。
- `/dev/snvme<X>n<Y>`：绑定成功后的普通块设备。

当前推荐使用 B3 dynamic queue-group 流程：

```text
SNVM_CHRDEV_CREATE
-> NVM_SET_KERNEL_IOQ_CAP
-> SNVM_DEVICE_BIND
-> NVM_GET_DEV_INFO
-> NVM_CREATE_QUEUE_GROUP
-> NVM_MAP_* memory
-> NVM_ADD_USER_QUEUE
-> 写 SQE + 写 BAR0 doorbell + 轮询 CQE
-> NVM_DESTROY_QUEUE_GROUP
```

### 2.2 libnvm

目录：`backends/local/nvme/libnvm/`

`libnvm` 是用户态封装层，负责：

- 调用 SNVMe ioctl；
- `mmap()` NVMe BAR0；
- 注册 SQ/CQ 和数据缓冲区；
- 管理 queue group；
- 把 doorbell 指针交给加速器侧代码。

当前实现直接依赖 CUDA，因此迁到 910C 后需要形成 Ascend/CANN 版本，或者抽出
accelerator backend 接口。

### 2.3 libgeminifs 与 NVMeService

- `filesystems/ext4/libgeminifs/`：上层 GeminiFS 文件系统逻辑。
- `backends/local/NVMeService/`：SNVMe 生命周期和多客户端接入管理。

这两层应当放到后续阶段。先证明 SNVMe CPU 路径和 NPU direct 路径成立，再迁移
完整 GeminiFS，定位成本会低很多。

## 3. 当前实现绑定 NVIDIA 的具体位置

### 3.1 NPU 内存导出给 NVMe DMA

`snvme-5.15.0-public/nvfs-p2p.c` 在模块初始化时动态查找以下 NVIDIA 驱动符号：

```text
nvidia_p2p_get_pages
nvidia_p2p_put_pages
nvidia_p2p_dma_map_pages
nvidia_p2p_dma_unmap_pages
nvidia_p2p_free_dma_mapping
nvidia_p2p_free_page_table
```

`map.c` 使用这些接口完成：

```text
加速器虚拟地址
-> pin device pages
-> 针对 NVMe PCI device 建立 DMA mapping
-> 获取 NVMe 可用的 DMA/bus address
-> 写入 NVMe SQ/CQ 或 PRP/SGL
```

华为侧需要提供语义等价能力。仅有 `aclrtMalloc()` 并不够，因为 SNVMe 还必须获得
“目标 NVMe 控制器可以使用的 DMA 地址”。

### 3.2 AIV 访问 NVMe doorbell

当前 CUDA 路径是：

```text
NVMe BAR0
-> /dev/ssnvme<N> mmap 到 CPU VA
-> cudaHostRegister(..., cudaHostRegisterIoMemory)
-> cudaHostGetDevicePointer()
-> CUDA kernel 写 sq_tail/cq_head doorbell
```

AIV 迁移需要回答：AIV 是否能获得第三方 PCIe BAR0 MMIO 区域对应的 device-visible
地址，并从核函数中执行 32-bit MMIO load/store。

### 3.3 写入顺序

当前 CUDA kernel 在写 SQE 后调用 `__threadfence_system()`，再写 SQ doorbell。
华为 AIV 侧必须提供等价的 system-scope ordering 语义，确保 NVMe 读取 SQE 时内容
已经对 PCIe peer 可见。

## 5. 分阶段排查方案

### 阶段 0：采集华为服务器基线信息

先确认服务器形态、内核、架构、NPU 驱动和 NVMe 拓扑：

```bash
uname -a
uname -r
uname -m
cat /etc/os-release
ls -l /lib/modules/$(uname -r)/build
grep -E 'CONFIG_MODULE_SIG|CONFIG_IOMMU|CONFIG_VFIO' /boot/config-$(uname -r)
lspci -Dnn
lspci -Dnn | grep -i -E 'non-volatile|nvme'
lspci -tv
lsmod
dmesg -T | tail -n 300
npu-smi info
```

需要记录：

| 项目 | 目的 |
|---|---|
| `uname -r` | 判断是否已有可用 SNVMe baseline |
| `uname -m` | 判断是 `x86_64` 还是 `aarch64`，测试代码中有 x86 MMIO 假设需要审计 |
| NVMe BDF | 后续传给 smoke test，例如 `0000:08:00.0` |
| NPU 与 NVMe PCIe 拓扑 | 判断是否同一 PCIe Switch、是否经过 IOMMU/桥 |
| 内核 module signing | 判断自编译 `.ko` 是否可直接 `insmod` |
| IOMMU/SMMU 配置 | 判断 peer DMA 地址能否正确建立 |
| 物理机、容器或虚拟机 | peer DMA 和 BAR 映射通常受部署形态限制 |

输出建议保存为一个环境快照：

```bash
mkdir -p /tmp/geminifs-910c-check
uname -a > /tmp/geminifs-910c-check/uname.txt
lspci -Dnn > /tmp/geminifs-910c-check/lspci.txt
lspci -tv > /tmp/geminifs-910c-check/lspci-tree.txt
lsmod > /tmp/geminifs-910c-check/lsmod.txt
dmesg -T > /tmp/geminifs-910c-check/dmesg-before.txt
npu-smi info > /tmp/geminifs-910c-check/npu-smi.txt
```

### 阶段 1：判断是否需要新增华为内核 baseline

仓库当前 baseline：

| 目录 | 对应内核 |
|---|---|
| `snvme-5.15.0-public` | Linux mainline 5.15.0 参考实现 |
| `snvme-5.4.241-1-tlinux4-0017` | TencentOS/OpenCloudOS 5.4.241 |

如果华为服务器的 `uname -r` 不匹配，新增：

```text
backends/local/kernel_modules/snvme-<华为服务器 uname-r 前缀>/
```

迁移方法按 `backends/local/kernel_modules/PORTING.md` 第 7 节执行：

1. 选最接近的旧 SNVMe baseline。
2. 获取华为服务器内核对应源码中的 `drivers/nvme/host/`。
3. 用 stock-old、stock-new、SNVMe-fork 做 3-way merge。
4. 重新审计 `nvme_probe`、`nvme_setup_io_queues`、MSI-X 分配、reset、remove、
   lock order 和设备命名。
5. 保持 `libnvm/include/ioctl.h` 的 UAPI 不变。

注意：`snvme-5.15.0-public` 是参考 baseline，不表示任意 5.15.x 厂商内核都能直接
使用。厂商 backport 会改变 NVMe 和内核 API。

### 阶段 2：先做 host-only SNVMe 验证

目标：不依赖 NPU direct memory，先验证 SNVMe 基础能力：

```text
模块加载
-> /dev/snvm_control
-> 创建 /dev/ssnvme<N>
-> mmap NVMe BAR0
-> host pinned pages
-> B3 queue group
-> host SQ/CQ
-> CPU 写 doorbell
-> NVMe IO round-trip
```

当前代码有一个前置障碍：`snvme.ko` 初始化时强制调用
`nvfs_nvidia_p2p_init()`，找不到 NVIDIA 符号就直接返回 `-EOPNOTSUPP`。
因此迁移实现的第一个小改动应是把 accelerator P2P backend 抽象化，并允许
`host-only` 模式加载模块。此时 NPU memory ioctl 可以明确返回
`-EOPNOTSUPP`，但 host memory 路径仍应可运行。

host-only 测试顺序：

```bash
cd backends/local/kernel_modules/test
make

# 安全：不 bind，不写盘
sudo ./snvme_smoke_qgroup <NVME_BDF>
sudo ./snvme_smoke <NVME_BDF>

# 破坏性：必须使用可清空的测试 NVMe
sudo ./snvme_smoke_addq <NVME_BDF>
sudo ./snvme_smoke_recycle <NVME_BDF>
sudo ./snvme_smoke_io <NVME_BDF>
```

说明：

- `snvme_smoke` 的默认模式会测试字符设备、host map 和 BAR0 `mmap()`。
- `snvme_smoke_io` 会写 NVMe LBA，只能在专用测试盘执行。
- 每轮测试前后保存 `dmesg -T`。
- 不要在生产挂载盘上运行带 bind 或写盘的测试。

### 阶段 3：验证 NPU 内存能否导出给 NVMe DMA

这一阶段先不让 AIV 写 doorbell。由 CPU 发起 doorbell，单独验证：

```text
NPU device memory
-> 华为驱动 pin/export pages
-> 针对 NVMe BDF 建立 DMA mapping
-> 得到 NVMe 可用 DMA address
-> 填 PRP/SGL
-> CPU 写 doorbell
-> NVMe DMA 读写 NPU memory
```

建议华为侧先提供最小 probe 内核模块或 ioctl，不要直接塞进完整 SNVMe：

```text
ascend_p2p_get_pages(npu_va, len, &page_table, invalidation_cb, data)
ascend_p2p_dma_map_pages(nvme_pdev, page_table, &mapping)
ascend_p2p_dma_unmap_pages(nvme_pdev, page_table, mapping)
ascend_p2p_put_pages(npu_va, page_table)
ascend_p2p_free_dma_mapping(mapping)
ascend_p2p_free_page_table(page_table)
```

函数名不要求一致，但语义必须覆盖。验证通过后，再把该 backend 接入
`snvme-*/map.c`。

### 阶段 4：验证 AIV 能否直接写 NVMe BAR0 doorbell

这是第二个独立核心问题。最小验证程序只需要：

1. CPU 侧 `mmap()` `/dev/ssnvme<N>` 的 BAR0。
2. 通过华为 runtime/驱动接口将该 MMIO 区域映射为 AIV 可访问地址。
3. AIV 核读取 CAP 或写入专用测试 queue 的 SQ tail doorbell。
4. 在 AIV 核中执行等价于 system-scope fence 的指令，再写 doorbell。
5. 由 CPU 和 NVMe CQ 双侧观察结果。

如果 AIV 不允许直接访问第三方 PCIe MMIO，可以保留一个 CPU doorbell 代理作为
功能降级路径，但这只能用于功能验证，不能视为完成 GeminiFS 原始 direct-IO
语义和性能目标。

### 阶段 5：移植用户态 CUDA 依赖

内核能力验证成功后，再做：

```text
cudaMalloc                    -> aclrtMalloc 或华为确认的可导出内存分配接口
cudaHostRegister(IoMemory)    -> 华为确认的第三方 BAR MMIO 注册接口
cudaHostGetDevicePointer      -> 华为确认的 AIV 可见地址查询接口
__threadfence_system          -> 华为确认的 AIV system-scope fence
CUDA kernel                   -> Ascend C / AIV kernel
```

公开 CANN 文档可以确认 `aclrtMallocHost`、`aclrtMalloc`、`aclrtMemcpy*` 和
Device 间 peer-access 能力，但这些公开 API 不能直接证明第三方 NVMe peer DMA
和 AIV 写第三方 BAR MMIO 已开放。

### 阶段 6：再运行 NVMeService 和完整 GeminiFS

在 kernel smoke 和 Ascend direct smoke 都通过后，再迁移并验证：

```text
libnvm Ascend backend
-> NVMeService
-> libgeminifs
-> 完整 GeminiFS workload
```

## 6. 和华为 AIV/驱动团队对接的 API 清单

建议把下面表格直接作为对接 checklist。每一项要求华为给出：

- 是否支持 910C；
- 适用服务器形态；
- 公开 API、内部 API 或需要新增 API；
- 头文件、库、内核模块和版本；
- 最小 demo；
- 权限、签名、IOMMU 和拓扑约束；
- 错误码与日志获取方式。

| 编号 | 需要确认的能力 | GeminiFS 用途 | 缺失时的结果 |
|---|---|---|---|
| A1 | pin/export 一段 NPU device virtual address 对应的物理页或 IOVA | 导出 SQ/CQ 和 data buffer | NVMe 无法直接 DMA 到 NPU 内存 |
| A2 | 针对指定第三方 PCIe NVMe `struct pci_dev` 建立 peer DMA mapping | 获取 NVMe 可用 DMA/bus address | PRP/SGL 无法填写 |
| A3 | unmap、put pages、free mapping、free page table | queue group 销毁和异常退出清理 | 泄漏、无法卸载模块、重启后失败 |
| A4 | NPU 内存失效回调 | 处理进程退出、free、reset | 可能出现 use-after-free 或 DMA 到失效页 |
| A5 | 返回 page size、页数、DMA 地址数组、连续性信息 | 正确构造 PRP/SGL | 地址对齐或跨页 IO 错误 |
| A6 | 将第三方 NVMe BAR0 MMIO 映射成 AIV 可访问地址 | AIV 直接写 doorbell | 只能 CPU 代理提交 |
| A7 | AIV 对该 MMIO 区域执行 32-bit load/store | 更新 SQ tail / CQ head | doorbell 无法直接敲响 |
| A8 | AIV system-scope memory fence | 保证先写 SQE 再写 doorbell | NVMe 可能读到未完成 SQE |
| A9 | cache flush/invalidate 或一致性规则 | CQ polling、data buffer 可见性 | CQE 或数据可能不可见 |
| A10 | NVMe reset、NPU reset、进程 kill 后资源回收语义 | 稳定运行和故障恢复 | 第二轮测试或 reset 后失败 |
| A11 | 物理机、容器、虚拟机、SMMU/IOMMU 限制 | 明确部署边界 | 实验机通过但部署环境失败 |
| A12 | `.ko` 编译、符号导出和签名流程 | 加载 SNVMe/适配模块 | 代码完成但无法部署 |

### 建议向华为团队提的关键问题

1. 910C 是否支持第三方 PCIe endpoint（NVMe SSD）直接 DMA 读写 NPU HBM？
2. 是否存在类似 NVIDIA `nvidia_p2p_get_pages()` 和
   `nvidia_p2p_dma_map_pages()` 的内核接口？接口是否允许外部 `.ko` 调用？
3. 该接口返回的是物理地址、IOVA 还是针对 peer device 的 DMA 地址？经过 SMMU
   时如何建立映射？
4. AIV 核是否允许访问第三方 PCIe BAR MMIO？如何把 NVMe BAR0 注册成 AIV
   可访问地址？
5. AIV 中哪条 fence/barrier 能保证 global-memory 写入先于 PCIe MMIO doorbell
   写入对 peer device 可见？
6. NPU memory free、进程异常退出、NVMe reset、NPU reset 时，谁负责通知并释放
   peer mapping？
7. 910C 服务器推荐的 PCIe 拓扑是什么？NVMe 和 NPU 是否必须在同一个 PCIe
   Switch 下？是否支持跨 Switch？
8. 开发环境是否允许加载 unsigned out-of-tree `.ko`？生产环境的签名流程是什么？

## 7. 故障定位矩阵

| 失败点 | 首要检查 | 责任边界 |
|---|---|---|
| 编译 SNVMe 失败 | `uname -r`、内核 headers、厂商 backport、baseline 是否匹配 | Linux baseline 迁移 |
| `insmod snvme.ko` 报找不到 `nvidia_p2p_*` | 当前代码强绑定 NVIDIA，需要 host-only 或 Ascend backend | SNVMe accelerator backend |
| `insmod` 报 `Required key not available` | `CONFIG_MODULE_SIG_FORCE`、Secure Boot、华为签名服务 | 服务器内核策略 |
| `/dev/snvm_control` 不出现 | 模块 init 日志、字符设备注册、符号加载 | SNVMe 基础模块 |
| `SNVM_DEVICE_BIND` 失败 | NVMe BDF、原驱动解绑、udev autoprobe、`dmesg` | SNVMe PCI bind |
| `snvme_smoke_io` CPU 路径失败 | host page pin、BAR0 mmap、MSI-X cap、B3 queue group | SNVMe core |
| NPU memory pin/export 失败 | 分配方式、页对齐、驱动 API、进程权限 | 华为 runtime/驱动 |
| NPU pages 可导出但 DMA map 失败 | NVMe peer BDF、IOMMU/SMMU、PCIe ACS、拓扑 | 华为驱动和平台 |
| CPU doorbell 可用，AIV doorbell 不可用 | BAR0 注册、AIV MMIO 权限、地址转换 | 华为 AIV/runtime |
| AIV 能写 doorbell 但 IO 超时或数据错 | fence、cache coherence、PRP/SGL、page size | AIV 指令语义和 backend |
| 第一轮通过，第二轮失败 | unmap、失效回调、queue delete、QID 回收 | cleanup/reset 语义 |
| reset 后失败 | user queues 是否销毁并重建、mapping 是否失效 | SNVMe reset 与华为驱动 |

## 8. 建议的验收门槛

### M0：环境可开发

- 能获得华为服务器准确内核源码和 headers。
- 能加载测试 `.ko`，或明确签名流程。
- 有一块允许清空的 NVMe 测试盘。

### M1：SNVMe host-only

- `/dev/snvm_control` 和 `/dev/ssnvme<N>` 正常。
- `snvme_smoke`、`snvme_smoke_qgroup` 通过。
- `snvme_smoke_addq`、`snvme_smoke_recycle`、`snvme_smoke_io` 在测试盘通过。

### M2：NPU peer DMA

- NVMe 能直接 DMA 读写 NPU memory。
- 至少覆盖单页、多页、PRP list、重复 map/unmap 和异常退出。

### M3：AIV direct doorbell

- AIV 核可写 BAR0 doorbell。
- 顺序语义正确。
- 连续 4 轮 queue group 创建和销毁通过。

### M4：稳定性

- kill -9 后无 mapping 泄漏。
- NVMe reset 后可恢复。
- NPU reset 或进程退出后可恢复。
- 多 NVMe、多 NPU 拓扑下行为清晰。

### M5：完整 GeminiFS

- Ascend 版 libnvm、NVMeService、libgeminifs 通过功能和性能测试。

## 9. 建议的代码改造边界

不要把华为逻辑散落到 `pci.c`。建议先抽象 accelerator P2P backend：

```text
snvme_accel_backend
├── init / exit
├── get_pages / put_pages
├── dma_map_pages / dma_unmap_pages
├── free_dma_mapping / free_page_table

```
