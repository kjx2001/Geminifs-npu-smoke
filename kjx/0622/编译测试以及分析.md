# 0622 — 五个 smoke 测试能否跑通？编译/测试步骤 + 逐测试分析

> 结论先行：**能。** 在「内核 5.15→5.10 迁移正确」这个前提下，
> `test/` 目录里的 **5 个 `.c` 测试**（snvme_smoke / qgroup / recycle / addq / io）
> 理论上全部可以跑通，而且**完全不需要 NPU、也不需要替换任何 NPU peer-DMA 代码**。
> 真正强绑定 NPU 的只有第 6 个 `.cu` 测试（snvme_smoke_gpu），那是后面「线 B」的事。
>
> 下面把「为什么能」「怎么编译」「怎么测」「每个测试万一跑不通该查哪里」讲清楚。

## 0. 你问的核心问题，直接回答

> 「如果迁移正确，先不管 GPU/NPU 的函数差距，上面这五个测试都可以跑通吗？
> 因为不需要 NPU 自己去敲 doorbell，靠 CPU 帮忙的话，应该可以跑通？
> 还是说仅跑前五个测试也涉及到强相关、需要替换成 NPU 对应代码？」

**答：五个 `.c` 测试 100% 走 Host/CPU 路径，不碰任何 NPU/GPU 代码，所以只要内核迁移正确就能跑通。**

依据（已逐文件核对）：

1. **五个测试本身只依赖 libc + UAPI 头**。
   `grep` 了 5 个 `.c` 文件的 `#include`，全部只有 `<stdio.h>/<fcntl.h>/<sys/ioctl.h>/<sys/mman.h>...` 加一个 `"ioctl.h"`（UAPI），
   **没有任何 `cuda`/`nvidia`/`npu`/`acl` 头**。CUDA 只出现在 `snvme_smoke_gpu.cu`（第 6 个，不在你这五个里）。

2. **内核里 Host 路径和 GPU/NPU 路径是两条独立分支**。
   - Host 内存：`NVM_MAP_HOST_MEMORY` → `map_userspace()` → `get_user_pages()` + `dma_map_page()`（[map.c:287](../../backends/local/kernel_modules/snvme-5.10-npu/map.c#L287)）。**纯内核 API，和 NVIDIA/NPU 无关。**
   - 显存路径：`NVM_MAP_DEVICE_MEMORY` → `nvfs_nvidia_p2p_get_pages()`（[map.c:485](../../backends/local/kernel_modules/snvme-5.10-npu/map.c#L485)）。**这条才是要换成昇腾 HBM 的，五个 CPU 测试根本不调它。**
   - map.c 作者自己写了注释（map.c:447）：
     > 在没有 NVIDIA 驱动的华为机器上，这些 nvfs 函数返回 -ENOMEM，走不到，**所以第一阶段只用 host 路径**。

3. **敲 doorbell 是 CPU 干的，不是 NPU**。
   `snvme_smoke_io.c` 的 `mmio_writel()`（[snvme_smoke_io.c:361](../../backends/local/kernel_modules/test/snvme_smoke_io.c#L361)）：CPU `mmap` 进 BAR0，普通 `*addr = value` 写 doorbell。NPU/GPU 完全不参与。
   而且这个函数**已经做了 aarch64 适配**：x86 用 `sfence`，非 x86（含华为 aarch64）用 `__atomic_thread_fence(__ATOMIC_RELEASE)`。

4. **模块在没有 NVIDIA 的机器上也能 insmod**。
   pci.c 的 `nvme_init` 里，`nvfs_nvidia_p2p_init()` 失败时**只打 warning、继续加载**，进入 HOST-ONLY 模式（[pci.c:6645](../../backends/local/kernel_modules/snvme-5.10-npu/pci.c#L6645)，迁移修改 #1）。所以缺 NVIDIA 符号不影响这五个测试。

**一句话总结**：这五个测试验证的是「Linux 内核版本迁移线」（5.10 上能不能编译/加载/绑定 NVMe + 纯 CPU 队列 + BAR0），
和「NVIDIA→NPU peer-DMA 替换线」**完全正交**。能不能跑通，只取决于 5.15→5.10 的内核 API 迁移对不对，**不取决于 NPU 代码**。

## 1. 怎么单独编译 SNVMe 模块（不编译整个 Geminifs）

模块是**树外（out-of-tree）编译**，有独立 Makefile，不依赖顶层 CMake/Geminifs 构建。

```bash
cd /home/kjx/nds/Geminifs-npu-smoke/backends/local/kernel_modules/snvme-5.10-npu

# 干净重编
make clean

# 编译（host-only 测试推荐带 SNVME_NPU=1，链接 npu-p2p.o，彻底不碰 NVIDIA 私有符号）
make SNVME_NPU=1

# 产物：snvme-core.ko 和 snvme.ko
ls -l *.ko
```

说明：
- `KDIR` 默认 `/lib/modules/$(uname -r)/build`，华为服务器上就是它本机的 5.10 内核头，**不用动**。
  要指定别的内核源码树才需要 `make KDIR=/path/to/build`。
- **`SNVME_NPU=1` vs 不带**：
  - 不带（默认）→ 链接 `nvfs-p2p.o`（NVIDIA nv-p2p 私有 API 的 wrapper）。在华为机器上加载时找不到 nvidia 符号，**会打 warning，但仍然加载成功**（HOST-ONLY）。
  - 带 `SNVME_NPU=1` → 加 `-DSNVME_NPU`，改链接 `npu-p2p.o`（内核 dma-buf 实现），不依赖 NVIDIA 符号，更干净。
  - **对这五个 CPU 测试，两者都能用**（显存路径根本不被调用）。建议用 `SNVME_NPU=1`，省掉那条 warning，也更贴近 NPU 线。
- 如果 5.15→5.10 还有没修完的 API 报错，会在这一步暴露。把**新的报错符号名**发出来，按 0604/03 第 8 节的同法（`#if LINUX_VERSION_CODE < KERNEL_VERSION(5,15,0)` 守卫）继续修。

### 加载 / 卸载模块

```bash
# 加载（顺序固定：先 core 后 snvme）
sudo insmod snvme-core.ko
sudo insmod snvme.ko

# 验证：控制设备应出现
ls -l /dev/snvm_control
dmesg | tail -30          # 看加载日志，确认没有报错；HOST-ONLY 模式会有一条 nvidia 符号缺失的 warning，正常

# 卸载（顺序相反：先 snvme 后 core）
sudo rmmod snvme
sudo rmmod snvme_core     # 注意是下划线 snvme_core，不是 snvme-core
```

## 3. 测试运行顺序（按你笔记里的 ①~⑤，逐步加码）

先确认两件事：模块已加载（`/dev/snvm_control` 在）、找到要测的 NVMe 盘的 BDF：

```bash
lspci -D -d ::0108        # 列出所有 NVMe 控制器，第一列就是 BDF，如 0000:50:00.0
```

> ⚠️ 从第 3 个测试（recycle）开始会 **`--bind` / 绑定控制器**，是**破坏性**操作：
> 它会把这块盘从 in-tree `nvme` 驱动上抢过来。**务必用一块未挂载、无重要数据、专门做实验的 SSD。**
> io 测试还会**真的往 LBA 写数据**，盘必须是空的。

| 序 | 命令 | 是否 bind | 主要验证 | 是否碰 NPU |
|----|------|-----------|----------|-----------|
| ① | `sudo ./snvme_smoke 0000:50:00.0` | 否 | chrdev 工厂、host map/unmap、BAR0 mmap 参数校验、fd 回收、错误码 | 否 |
| ② | `sudo ./snvme_smoke_qgroup 0000:50:00.0` | 否 | CREATE/DESTROY_QUEUE_GROUP、跨 fd 隔离、fd close 级联清理 | 否 |
| ③ | `sudo ./snvme_smoke_recycle 0000:50:00.0` | **是** | nvme_probe、Admin Queue、Identify、RAW_ADMIN_CMD、unbind/rebind | 否 |
| ④ | `sudo ./snvme_smoke_addq 0000:50:00.0` | **是** | SET_KERNEL_IOQ_CAP、ADD_USER_QUEUE、Create/Delete I/O SQ·CQ、doorbell offset | 否 |
| ⑤ | `sudo ./snvme_smoke_io 0000:50:00.0` | **是+写盘** | CPU 填 SQE→敲 SQ doorbell→DMA→轮询 CQE→敲 CQ doorbell→读回校验 | 否 |

也可以用 Makefile 的便捷目标：`PCI=0000:50:00.0 make run`（①，加 `BIND=1` 才 bind）、`make run-qgroup`、`make run-recycle`、`make run-addq`、`make run-io`。

每跑一个，配合另一终端 `dmesg -w` 看内核日志。**前一个不过不要跳到下一个**——它们是依赖递进的（recycle 不过说明 probe/admin 有问题，就不该去建用户队列）。

## 4. 逐测试分析：万一跑不通，问题一定在「内核迁移」而非「NPU」

下面每个测试，列出它**实际压到哪段内核代码**，以及 5.15→5.10 迁移中**最可能出问题的点**。
注意：**所有风险点都是内核 API 迁移问题，没有一个是 NPU 问题。**

### ① snvme_smoke —— UAPI 冒烟（不 bind，风险最低）
- 压：`/dev/snvm_control` 的 `SNVM_CHRDEV_CREATE/REMOVE`、`/dev/ssnvmeN` 的 open/release、`NVM_MAP_HOST_MEMORY`/`UNMAP`、BAR0 `mmap` 参数校验、非法参数错误码。
- 走的内核文件：ctrl.c、ioctl.c、map.c 的 host 分支、pci.c 的 chrdev/mmap fops。
- 迁移风险点：
  - `get_user_pages()` 的签名跨版本不同（map.c 里已用版本守卫，见 map.c:242/245/247）——若 5.10 上参数对不上会编译失败，**编译期就暴露**，不会到运行期。
  - 基本不 bind、不碰 admin，**这一关过不了几乎一定是 chrdev/mmap 的 fops 注册或 host map 的 5.10 适配问题**。

### ② snvme_smoke_qgroup —— 队列组生命周期（不 bind）
- 压：`NVM_CREATE_QUEUE_GROUP` / `NVM_DESTROY_QUEUE_GROUP`、跨 fd 隔离（A fd 的 group B fd 不可见）、`close(fd)` 自动级联销毁。
- 走的内核文件：pci.c 里 qgroup 的 ioctl handler + per-fd owner 链表。
- 迁移风险点：纯内核软件资源管理（链表、mutex、ida），**和内核版本几乎无关**，更和 NPU 无关。过不了多半是 qgroup 代码本身在搬运时漏了字段，而非 5.10 差异。

### ③ snvme_smoke_recycle —— 绑定 + Admin（**第一道真正考验 5.10 NVMe core 的关**）
- 压：`SNVM_DEVICE_BIND` → `s_nvme_probe()` → Admin Queue 建立 → Identify Controller → `NVM_GET_DEV_INFO` → `NVM_RAW_ADMIN_CMD` 透传 → unbind/rebind。
- 走的内核文件：pci.c 的 `s_nvme_probe`/`s_nvme_setup_io_queues`、core.c 的 controller init/reset/namespace scan。
- 迁移风险点（**这里最容易踩 5.10 雷**）：
  - `blk_execute_rq` / `blk_execute_rq_nowait` 5.10 签名不同（0605 batch 1 已修，需在真盘上验证）。
  - `nvme_init_ctrl_finish` / `set_capacity_and_notify` 等 5.10 差异（已用守卫修，需运行期确认）。
  - `device_add_disk` 5.10 返回 void、multipath 的 `blk_alloc_disk` 等（已修）。
  - **若这关挂了**：先看 `dmesg`，大概率是 probe 路径里某个 5.10 API 行为差异（不是 NPU）。

### ④ snvme_smoke_addq —— 创建用户 SQ/CQ（**考验 §3.2 那处外科手术改动**）
- 压：`NVM_SET_KERNEL_IOQ_CAP`（bind 前设 cap=36）→ bind → `NVM_ADD_USER_QUEUE`（Create I/O CQ + Create I/O SQ）→ 拿 doorbell offset → `NVM_DESTROY_QUEUE_GROUP` 级联删。
- 走的内核文件：pci.c 的 `s_nvme_setup_io_queues` 里的 **cap 分支**（PORTING.md §3.2 唯一的 probe 侧改动）、ADD_USER_QUEUE handler。
- 迁移风险点：
  - **cap 分支的插入点**：必须在 5.10 的 `pci_alloc_irq_vectors_affinity()`（MSI-X 协商）**之后**、tagset 定型**之前**。5.10 的 helper 布局和 5.15 不同，插错位置会要么扭曲 MSI-X 分配，要么 cap 不生效。
  - **`ctrl_max_io_queues` 必须记录 cap 前的 `nr_io_queues`**（用户 QID 池上界靠它）。漏了→用户池为空→`NVM_ADD_USER_QUEUE` 返回 `-EAGAIN`/`-ENODEV`。
  - 这些**全是 5.10 内核移植的正确性问题**，依然和 NPU 无关。

### ⑤ snvme_smoke_io —— 真实 IO 往返（**整条 Host 数据面**）
- 压：CPU 填 SQE → 写 SQ tail doorbell → SSD DMA 读/写 Host data buffer（PRP）→ CPU 轮询 CQE phase 位 → 写 CQ head doorbell → 读回逐 LBA 校验。
- 走的内核文件：map.c host DMA + PRP、pci.c BAR0 mmap；用户态 `mmio_writel`。
- 迁移风险点：
  - **aarch64 doorbell 写序**：`mmio_writel` 已用 `__atomic_thread_fence(__ATOMIC_RELEASE)` 替代 x86 `sfence`（已适配）。这是 aarch64 上唯一需要留意的点，目前代码是对的；若数据校验偶发不一致，再回来看这条屏障是否够强（device 内存可能需要更强的 `dmb`）。
  - PRP 列表构造、`dma_map_page` 的 IO 地址正确性——属于 host map 迁移，非 NPU。

## 5. 结论与下一步

- **五个测试是「内核迁移线」的验收，不是「NPU 替换线」的验收。** 你现在能编译、能 insmod，说明编译期的 5.10 适配基本到位；接下来跑这五个就是在运行期逐段验证 probe / admin / 用户队列 / 数据面。
- **不需要等 NPU 任何东西**，也不需要改 `npu-p2p.c`/`nvfs-p2p.c`——它们服务的 `NVM_MAP_DEVICE_MEMORY` 在这五个测试里一次都不会被调到。
- 跑测试时若失败，**先 `dmesg`**，问题点一定落在第 4 节列的某个 5.10 内核 API 迁移项里，按 0604/03 第 8 节的「push→pull→把新报错发来→守卫修」流程继续。
- 这五关全绿之后，才是基线成立、可以开始「线 B」——把 `npu-p2p.c` 接上昇腾 HBM 的 pin/map 能力 + AIV 直接敲 doorbell（对接华为 AIV/驱动团队），并跑 `snvme_smoke_gpu` 的 NPU 版本。
