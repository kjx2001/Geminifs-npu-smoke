# B3 模块迁移到 openEuler：分阶段「拷贝→编译→测试」具体执行步骤

> 日期：2026-06-04
> 只考虑 **Geminifs_smoke（B3）**，不再管旧的 `Geminifs`（B0）。
> 配套：`01测试分析以及后续迁移计划.md`（测试逐函数注释 + 能力阶梯 + 宏观计划）。本文是它的**落地执行版**，回答你的两个具体问题并给出一步步命令。

## 0. 先回答你的两个问题（很重要，决定整个打法）

### 问题 1：为什么要三方合并？直接拷贝过去、哪报错改哪、全用 5.15 不行吗？

**第一次 bring-up，"直接拷贝 + 哪报错改哪"就是对的，我支持你这么做。** 三方合并是"做一个可长期维护的正式移植"才需要的严谨手法；对"先看看到底能不能跑通"这个目标，copy-then-fix 反馈更快、更适合新手。

但有一个**你必须知道的风险**，否则会踩坑：

> **编译通过 ≠ 行为正确。**
> 5.15 和 openEuler 5.10 的内核 API 差异分两种：
> - **编译期差异**（好对付）：函数签名变了、某个 API 5.10 没有 → 编译器**直接报错**，你照着改就行。
> - **静默语义差异**（要命）：结构体字段挪了位置、某函数多了"调用前必须持锁"的隐含前提、probe 初始化顺序变了 → **编译不报错，但运行时崩溃/挂死/数据错**。

所以正确策略是：
1. **先 copy + 改编译错误**，让它编过、能加载（快速拿到一个能跑的 .ko）。
2. **靠那 6 个 smoke 测试当安全网**去抓"静默语义差异"——这正是这些测试存在的意义。
3. **只有当某个改自原生的文件（主要是 `pci.c` / `core.c`）改报错改到一团乱、你看不懂"为什么 5.15 这么写"时**，才回头单独对那一个文件做三方 diff（拿 5.15 原生 nvme 和 SNVMe 的 5.15 版对比，看 SNVMe 到底动了哪几处），把那几处改动看明白再套到 5.10 上。

一句话：**全用 5.15、哪报错改哪，是合理的起手式；三方合并不是前置作业，而是"卡住时的查证工具"。**

### 问题 2：能不能只拷几个文件、做最简单的测试，然后再拷下一部分？

**"按文件拆"做不到，但你"分阶段、看到底哪部分挂"的思路完全正确——只是分阶段的"单位"不是文件，而是"测试"。** 原因：

- 模块最终链接成**两个 .ko**，对象集是固定的、文件之间强依赖：
  ```
  snvme-core.ko = core.o + ioctl.o + multipath.o + zns.o + hwmon.o
  snvme.ko      = nvfs-pci.o + nvfs-p2p.o + list.o + ctrl.o + map.o + pci.o
  ```
  `pci.c` 要用 `core.c`、`nvme.h`、`ioctl.c` 的符号；`ioctl.c` 要用 `map.c`、`ctrl.c`……**少拷任何一个都既编不出 .ko、也加载不了**。所以"拷一小部分先编译"在这个项目里不成立。

- **但是**——那 6 个测试本身就是天然的"分阶段"，每个测试只考验模块的**一部分能力/代码路径**。所以正确的分阶段是：
  > **一次性把整个目录拷过去 → 想办法编过 → 想办法加载 → 然后按测试的能力顺序逐个跑；第一个失败的测试，就精确告诉你模块的哪条代码路径在 5.10 上坏了。**

这张表是你"看哪部分挂"的地图：

| 顺序 | 测试 | 是否 bind | 主要考验模块的哪部分 | 失败 → 重点查哪个文件 |
|---|---|---|---|---|
| ① | `snvme_smoke_qgroup` | 否 | 字符设备 + queue group 容器 + host 内存映射 | `ctrl.c`(chrdev) `ioctl.c`(qgroup) `map.c`(host map) |
| ② | `snvme_smoke` | 否(默认) | BAR0 mmap + CAP 读 + host SQ/CQ 映射 | `pci.c`(BAR0 mmap 路径) `map.c` |
| ③ | `snvme_smoke_recycle` | **是** | **bind/probe 全流程** + admin 队列 + admin 透传 | `pci.c`(s_nvme_probe / reset_work / admin queue) ← **5.15→5.10 差异最致命的地方** |
| ④ | `snvme_smoke_addq` | 是 | 把 host SQ/CQ 注册成 I/O queue（Create I/O CQ/SQ） | `pci.c`(adapter_alloc_*_user / QID 池 / doorbell 偏移) |
| ⑤ | `snvme_smoke_io` | 是(写盘) | CPU 全程写 SQE+敲 doorbell+轮询，真实读写 | BAR0 doorbell 映射、DMA 地址正确性 |
| ⑥ | `snvme_smoke_gpu` | 是 | **需要 NVIDIA**，host-only 模式跑不了 | NPU 阶段才做，本次**跳过** |

> **关键洞察**：①② 不 bind，只验证"字符设备 + 内存映射 + queue group"这层，**最先能绿**；③④⑤ 要 bind，会走 `pci.c` 的 probe 路径——**这才是 5.15→5.10 移植真正的硬骨头**。所以天然的推进节奏是：**先让 ①② 绿（证明上层 ioctl/map/chrdev 在 5.10 OK），再啃 ③ 的 bind/probe（最难），③ 过了 ④⑤ 通常就顺了。**

## 2. 阶段 A：整目录拷贝 + 第一次编译

### A.1 准备（在 NPU 服务器上）
```bash
uname -r          # 记下，例如 5.10.0-60.18.0.50.oe2203.aarch64
uname -m          # 记下架构：aarch64 还是 x86_64
ls /lib/modules/$(uname -r)/build      # 必须存在！没有就装内核头：
                                       #   openEuler: sudo yum install kernel-devel-$(uname -r)
lspci -D -d ::0108                      # 记下要测试的 NVMe BDF，例如 0000:08:00.0
```
> 准备一块**可以清空的专用测试盘**（③④⑤ 会 bind/写盘）。绝不能用挂着数据的盘。

### A.2 拷贝整个 B3 模块目录
把这一整个目录拷到 NPU 服务器（用 scp/rsync/git 均可）：
```
Geminifs_smoke/backends/local/kernel_modules/snvme-5.15.0-public/
```
连带把 UAPI 头也带上（模块的 `pci.c`/`ioctl.c`/`core.c` 会 `#include "ioctl.h"`）：
```
Geminifs_smoke/backends/local/nvme/libnvm/include/ioctl.h
```
建议在 NPU 服务器上这样放，并复制成 5.10 的工作目录：
```bash
# 假设你把 Geminifs_smoke 整个 clone/拷到了 ~/Geminifs_smoke
cd ~/Geminifs_smoke/backends/local/kernel_modules
cp -r snvme-5.15.0-public snvme-5.10-openeuler     # 在副本上改，保留原始参照
cd snvme-5.10-openeuler
```

### A.3 写一个最小 Makefile（绕开 CMake 占位符）
原始 `Makefile.in` 里有 `@module_root@` 等占位符，是给顶层 CMake 渲染用的。我们自己手写一个独立 Makefile，直接在源码目录里编：
```bash
cat > Makefile <<'EOF'
# 树外编译 snvme-core.ko + snvme.ko
KDIR ?= /lib/modules/$(shell uname -r)/build
# UAPI 头 ioctl.h 的位置（按你的实际路径改）
UAPI_INC := $(src)/../../nvme/libnvm/include

obj-m += snvme-core.o
obj-m += snvme.o

snvme-core-y                         := core.o ioctl.o
snvme-core-$(CONFIG_NVME_MULTIPATH)  += multipath.o
snvme-core-$(CONFIG_BLK_DEV_ZONED)   += zns.o
snvme-core-$(CONFIG_NVME_HWMON)      += hwmon.o

snvme-objs := nvfs-pci.o nvfs-p2p.o list.o ctrl.o map.o pci.o

ccflags-y += -I$(UAPI_INC)

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules
clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
EOF
```
> 说明：`$(src)` 在内核 kbuild 里指向源码目录；`-I` 把 UAPI 头加进搜索路径。如果你把 ioctl.h 放别处，改 `UAPI_INC` 即可。

### A.4 第一次编译，看报错
```bash
make 2>&1 | tee build-1.log
```
你**几乎一定**会遇到这 3 类报错，按这个顺序处理：

**(1) `fatal error: nv-p2p.h: No such file or directory`（确定会遇到）**
来源：`nvfs-p2p.c` 和 `nvfs-p2p.h` 里 `#include "nv-p2p.h"`，这是 NVIDIA GPU 驱动的头，NPU 服务器上没有。
> 这个文件属于"GPU/device 内存"路径，而本次 5 个 host 测试**根本不用它**。两种解法（推荐先用解法 A 最快）：
>
> **解法 A（最快，先跑起来）**：从 NVIDIA 开源驱动 `open-gpu-kernel-modules` 里取一份 `nv-p2p.h`（它只是一堆类型定义，能让 `nvfs-p2p.c` 编过；运行时它靠 `symbol_get` 找 `nvidia_p2p_*`，找不到会优雅失败 → 正好进入 host-only）。把 `nv-p2p.h` 放进当前目录即可。
>
> **解法 B（更干净，长期用）**：把 nvfs 整个从编译里拿掉——`snvme-objs` 去掉 `nvfs-pci.o nvfs-p2p.o`，再把 `pci.c`/`map.c` 里调用 nvfs 的入口（如 `nvfs_nvidia_p2p_init`、device memory 映射）改成"host-only 桩"：直接返回 0 或 `-EOPNOTSUPP`。改动多一点，但产出的模块更纯净、不带任何 NVIDIA 痕迹。
>
> 第一次建议用 **A**，等 ①②③④⑤ 都验证完、要做正式版时再换 **B**。

**(2) 5.15 → 5.10 内核 API 差异（数量取决于你的内核）**
典型症状和**可能**遇到的（openEuler 5.10 有大量 backport，不一定全中，以编译器实际报错为准）：

| 报错关键字 | 含义 | 怎么改 |
|---|---|---|
| `blk_mq_alloc_disk` / `blk_alloc_disk` 未声明 | 5.14 才引入的磁盘分配 API | 5.10 用 `blk_mq_init_queue` + `alloc_disk`/`device_add_disk`，按 5.10 的 `core.c` 写法改 |
| `set_capacity_and_notify` 未声明 | 5.15 API | 5.10 用 `set_capacity` + `revalidate_disk_size` |
| `nvme_init_ctrl_finish` 未声明 | 5.15 改的名 | 5.10 是 `nvme_init_identify`（`snvme-rename.sed` 注释也提到这点） |
| `BIO_MAX_VECS` 未声明 | 5.12 改的名 | 5.10 是 `BIO_MAX_PAGES` |
| `struct nvme_ctrl`/`nvme_dev` 某字段不存在 | 结构体字段版本差 | 对照 5.10 的 `nvme.h` 改字段名/去掉 |

> **方法论比清单更重要**：内核编译报错就看"哪个函数/字段未声明" → 去 `/lib/modules/$(uname -r)/build/include` 和 openEuler 那份 `drivers/nvme/host/`（你机器上有 `kernel-openEuler-22.03-LTS-drivers-nvme/`）里 `grep` 这个名字，看 5.10 叫什么、签名是什么，照着改。**改不动、看不懂某处为什么这么写时**，才对那个文件做三方 diff（见问题 1）。

**(3) `ioctl.h: No such file` 或 UAPI 结构体未定义**
说明 `-I` 路径没对。确认 `UAPI_INC` 指向真正放 `ioctl.h` 的目录，重编。

### A.5 阶段 A 完成判据
```bash
ls -l snvme-core.ko snvme.ko       # 两个 .ko 都生成 = 阶段 A 完成
```

## 3. 阶段 B：让模块能加载（host-only 改动）

编出 .ko 不等于能加载。`pci.c` 在模块初始化时有个**确定的拦路点**（我已定位）：

```
pci.c:6066    if(nvfs_nvidia_p2p_init()) {
pci.c:6068        ret = -EOPNOTSUPP;     // ← 没有 NVIDIA 时这里直接让整个模块加载失败
              }
pci.c:6121    module_init(nvme_init);
```

### B.1 改 pci.c，让 p2p 初始化失败时进入 host-only 而不是拒绝加载
把 6066 那段从"失败就 `-EOPNOTSUPP` 返回"改成"失败就打一条 warning、继续加载，进入 host-only 模式"。最小改法（示意，按实际代码微调）：
```c
/* 原：
 *   if (nvfs_nvidia_p2p_init()) {
 *       ret = -EOPNOTSUPP;
 *       goto <错误标签>;
 *   }
 * 改成： */
if (nvfs_nvidia_p2p_init()) {
    pr_warn("snvme: NVIDIA p2p unavailable, running in HOST-ONLY mode "
            "(device-memory ioctls will return -EOPNOTSUPP)\n");
    /* 不再 return/-EOPNOTSUPP，继续走下去 */
}
```
> 这样：host 内存路径（NVM_MAP_HOST_MEMORY 等，5 个测试用的）全部正常；GPU/device 内存路径（NVM_MAP_DEVICE_MEMORY）在没有 NVIDIA 时该返回 `-EOPNOTSUPP` 就返回——这正是我们要的。

> 如果阶段 A 用了**解法 B**（把 nvfs 拿掉），这里 `nvfs_nvidia_p2p_init` 已被你改成返回 0 的桩，本步可能不用再改。

### B.2 重新编译、加载
```bash
make
sudo insmod snvme-core.ko
sudo insmod snvme.ko
ls -l /dev/snvm_control            # 出现（mode 0666）= 阶段 B 完成
dmesg -T | tail -40               # 应看到 host-only 的 warning 和 chrdev 注册日志
```
**常见加载失败**：
- `Required key not available` → 内核开了强制模块签名（`CONFIG_MODULE_SIG_FORCE`）。`grep CONFIG_MODULE_SIG_FORCE /boot/config-$(uname -r)` 确认；要么走签名流程，要么换一台没开强制签名的开发机（详见 PORTING.md §6.1）。
- `Unknown symbol in module` → 还有没改名的导出符号和 in-tree `nvme` 冲突，或某内核符号没找到；看 `dmesg` 指出的符号名继续修。

## 4. 阶段 C：按测试能力顺序逐个跑

### C.1 编译测试程序
```bash
cd ../test          # 回到 test 目录
make                # 没有 nvcc 会自动跳过 snvme_smoke_gpu，其余照常编出
```
> 注意：测试用的 UAPI 头要和你模块用的**同一个 ioctl.h**，否则 ioctl 号对不上。test 的 Makefile 已指向 `../../nvme/libnvm/include`，和模块一致，无需改。

### C.2 逐个跑（先安全后破坏性），每跑一个先存 dmesg
```bash
BDF=0000:08:00.0     # 改成你的实际 BDF
log(){ sudo dmesg -C; }     # 跑每个测试前清空 dmesg，便于隔离

# ── 子阶段 C-1：不 bind，最先该绿 ──
log; sudo ./snvme_smoke_qgroup $BDF ; sudo dmesg -T | tail -30   # ① 字符设备+queue group+host map
log; sudo ./snvme_smoke        $BDF ; sudo dmesg -T | tail -30   # ② BAR0 mmap + host SQ/CQ

# ── 子阶段 C-2：bind（用测试盘），probe 路径，最难 ──
log; sudo ./snvme_smoke_recycle $BDF ; sudo dmesg -T | tail -50  # ③ bind/probe + admin 透传
log; sudo ./snvme_smoke_addq    $BDF ; sudo dmesg -T | tail -50  # ④ 注册用户 I/O queue

# ── 子阶段 C-3：写盘，完整 IO ──
log; sudo ./snvme_smoke_io      $BDF ; sudo dmesg -T | tail -50  # ⑤ CPU 全程读写校验
```

### C.3 怎么判读 + 哪挂查哪
- 每个测试成功末尾打印 `all N steps passed`；**失败时最后一行 `[FAIL] step=N ...`** 就是断点。
- 对照本文第 0 节的能力表 + `01测试分析以及后续迁移计划.md` 第 2 节的步骤表，定位是模块哪条路径。
- **典型推进剧情**：
  - ①② 直接绿 → 说明 chrdev / mmap / map / queue group 这层在 5.10 上没问题，移植的"上半身"成功。
  - ③ 在 bind 后 `NVM_GET_DEV_INFO` 超时或 `dmesg` 里 probe 报错 → 这就是 5.15→5.10 **probe/blk-mq 差异**没处理干净，回到 `pci.c` 的 `s_nvme_probe` / `reset_work` / admin queue setup 对照 5.10 改。这是最值得花时间的地方。
  - ③ 过了，④⑤ 一般顺带就过；若 ④ 报 `SC=0x4101`（Invalid Queue Identifier），通常是 QID 池/`NVM_SET_KERNEL_IOQ_CAP` 相关，看 `pci.c` 用户队列分配。
- **aarch64 额外注意**：⑤ `snvme_smoke_io` 里 `mmio_writel` 的内存序，x86 是 `sfence`，aarch64 走 `__atomic_thread_fence`（已有分支，能编过）。若 ⑤ 出现"CQE 超时/数据偶发错"，重点怀疑这条 doorbell 写序在 aarch64 上的可见性，可能要换成更强的 barrier（如 `dma_wmb()` 语义）。

### C.4 记录矩阵（建议每轮填）
| 测试 | 编译 | 运行结果 | 断在哪步 | dmesg 关键行 | 初判原因 |
|---|---|---|---|---|---|
| qgroup | | | | | |
| smoke | | | | | |
| recycle | | | | | |
| addq | | | | | |
| io | | | | | |

跑到 ①~⑤ 全绿 = **达成 M1（纯 CPU 能力阶梯在 openEuler 上通过）**。这一步**完全不依赖华为开放任何 NPU 能力**，是你自己就能拿下的里程碑。

## 5. 之后（线 B，需要华为）

①~⑤ 全绿后，再进入 NPU 相关（数据缓冲→队列环→doorbell 逐步搬上 NPU HBM，最终对标 `snvme_smoke_gpu`）。这部分要华为开放 peer DMA 和 AIV doorbell 能力，按 `01测试分析以及后续迁移计划.md` 第 4 节的 A1~A12 清单对接。`snvme_smoke_gpu`（⑥）在 host-only 阶段跳过，等 NPU 能力就位后改写成 NPU 版再跑。

## 6. 一页速查（把这页贴在手边）

```
拷贝：  cp -r snvme-5.15.0-public snvme-5.10-openeuler   （+ 带上 ioctl.h）
编译：  写最小 Makefile → make → 修 3 类错：
          (1) nv-p2p.h 缺失   → 取 NVIDIA 的 nv-p2p.h 放进目录（或解法B去掉 nvfs）
          (2) 5.15→5.10 API   → 编译器报哪个就 grep 5.10 内核头改哪个
          (3) ioctl.h 路径     → 修 -I
加载：  改 pci.c:6066 让 p2p init 失败时进 host-only（不再 -EOPNOTSUPP）
        → insmod snvme-core.ko && insmod snvme.ko → 看 /dev/snvm_control
测试：  cd ../test && make
        ① qgroup  ② smoke      （不 bind，最先绿）
        ③ recycle ④ addq ⑤ io  （bind/写盘，probe 是硬骨头）
        ⑥ gpu = 跳过（要 NVIDIA）
判读：  最后一行 [FAIL] step=N = 断点；①②挂查 ctrl/ioctl/map，③④⑤挂查 pci.c probe 路径
里程碑：①~⑤ 全绿 = M1（纯 CPU，不靠华为）
```
