# 编过之后：在 NPU 服务器上加载模块 + 逐级跑测试（M1 验收手册）

> 日期：2026-06-05
> 前置：你已在 NPU 服务器（openEuler 5.10.0 / aarch64）把 `snvme-5.10-npu` 编出了 **`snvme-core.ko`** 和 **`snvme.ko`**（见 `03直接整体迁移分析和实现.md` 第 8 章 batch1~8 的 5.15→5.10 适配）。
> 本文接着讲：**加载模块 → 编译测试 → 按"安全→破坏性"顺序逐个跑 → 判读 → 排障 → M1 验收**。
> 关键认知（再强调）：这一层是**纯 CPU + host 内存 + 内核 NVMe 驱动**的 bring-up，**全程不碰 CANN、不需要 NPU 算力**。只要：openEuler 内核头 + gcc/make + **一块可清空的 NVMe 测试盘**。GPU 那条测试（`snvme_smoke_gpu`）host-only 阶段直接跳过。

---

## 0. 目录与产物速记

```
backends/local/kernel_modules/snvme-5.10-npu/   ← 模块源码，make 后产出两个 .ko
                              ├─ snvme-core.ko   ← 先加载（核心：chrdev /dev/snvm_control + ioctl）
                              └─ snvme.ko        ← 后加载（PCI 绑定/队列/map/p2p 包装）
backends/local/kernel_modules/test/             ← 本文要跑的 6 个 smoke 测试（C，libc-only）
backends/local/nvme/libnvm/include/ioctl.h      ← 测试用的 UAPI 头（Makefile 以相对路径找它）
backends/local/nvme/test/                        ← 另一套 libnvm 层测试，本文不用（M1 用 kernel_modules/test 就够）
```

加载成功的标志物：**字符设备 `/dev/snvm_control`（mode 0666）**——模块 `pci.c` 里 `device_create(..., "snvm_control")` 建的，测试程序全部通过它发 ioctl。

## 第 1 步——加载内核模块（insmod）

### 1.1 加载（顺序固定：先 core 再 snvme）
```bash
cd backends/local/kernel_modules/snvme-5.10-npu

sudo dmesg -C                       # 清屏，方便看本次日志
sudo insmod snvme-core.ko
sudo insmod snvme.ko

ls -l /dev/snvm_control             # 出现且 mode 0666 = chrdev 建好
dmesg -T | tail -40                 # 看本次加载日志
```

**期望看到**（host-only 模式的核心证据）：在 `dmesg` 里有我 batch 改动加的那条 warning：
```
snvme: nvidia_p2p* symbols not found; running in HOST-ONLY mode
       (device-memory ioctls will return -ENOMEM/-EOPNOTSUPP)
```
看到它 = 没有 NVIDIA 也能正常加载、模块进入**纯 CPU 路径**（这正是我们要的）。GPU/device 内存那条路被 `nvfs-p2p.c` 的包装函数在指针为 NULL 时自动挡掉，不会崩。

#### 1.1.1 你实际看到的两行日志——这是**正常**的（重要，别被 `nvidia-fs:` 吓到）

加载后 `dmesg` 里通常看到的是**这样两行**：
```
nvidia-fs: Unable to find symbol: nvidia_p2p_dma_unmap_pages
snvme: nvidia_p2p* symbols not found; running in HOST-ONLY mode
       (device-memory ioctls will return -ENOMEM/-EOPNOTSUPP)
```
**✅ 这完全正常，正是 host-only 设计预期的"握手"，不是报错、不用管。** 两行的来历：

1. **第一行 `nvidia-fs: Unable to find symbol: ...`** —— ⚠️ 注意：这条**也是我们 snvme 模块自己打的**，**不是**系统里另外装了一个 `nvidia-fs` 模块。
   - 原因：这套代码源自 NVIDIA 的 GPUDirect Storage（项目本名就叫 **nvidia-fs**），它的日志宏 `nvfs_msg`（`nvfs-core.h`）写死了用 `DEVICE_NAME "nvidia-fs"` 当打印前缀。我们沿用了这套代码，所以前缀还是 `nvidia-fs:`。
   - 它对应 `nvfs-p2p.c` 里 `nvfs_nvidia_p2p_init()` 的**第一步** `__symbol_get("nvidia_p2p_dma_unmap_pages")`：机器上没有 NVIDIA 驱动 → 找不到这个符号（**本就该找不到**）→ 打这条 + 返回失败。
2. **第二行 `snvme: ... running in HOST-ONLY mode`** —— 这是我们 batch1 改动在 `nvme_init()` 里**接住**上面那个失败后打的：不再像原版那样拒绝加载，而是打一句提示、继续进 host-only。

> 一句话：**第一行是"没找到 NVIDIA 符号"的内层提示，第二行是我们"那就走纯 CPU 模式"的兜底**——一内一外，成对出现就对了。
>
> **怎么进一步确认没有真的 nvidia-fs 在捣乱**（可选）：
> ```bash
> lsmod | grep -E "nvidia|nvme|snvme"   # 应只看到 snvme / snvme_core；没有 nvidia_fs / nvidia 行
> ls -l /dev/snvm_control                # 存在且 0666 = 我们的模块确实加载成功了
> ```
> 只要 `/dev/snvm_control` 在、`lsmod` 里是 `snvme`/`snvme_core`，就证明加载成功、那两行只是预期内的 host-only 提示。**可以直接进第 2 步。**

### 1.2 卸载（顺序相反）
```bash
sudo rmmod snvme && sudo rmmod snvme_core
```
> 模块名里的连字符 `-` 在 rmmod 时是下划线 `_`：`snvme` / `snvme_core`。

### 1.3 加载常见失败 & 处理
| dmesg / 报错 | 含义 | 处理 |
|---|---|---|
| `Required key not available` | 内核开了**强制模块签名** | `grep CONFIG_MODULE_SIG_FORCE /boot/config-$(uname -r)`；要么走签名流程，要么用一台没开强制签名的开发机 |
| `Unknown symbol XXX (err -2)` | 还有没改名、与系统自带 `nvme` 冲突的导出符号 | 按 dmesg 指出的符号名继续核（5.4 baseline 的 `snvme-rename.sed` 是参照，但 5.10 导出符号要重核）|
| `insmod snvme.ko` 报 `Unknown symbol` 指向 snvme-core 的符号 | core 没先加载/被自动卸了 | 确认 `lsmod | grep snvme`，core 必须在前 |
| 加载 snvme.ko 后**机器掉盘/系统盘异常** | snvme 抢绑了**系统在用**的 NVMe | 立刻 `rmmod`；务必只对**专用测试盘**做 `--bind` 类操作（见第 4 步） |

> ⚠️ **安全红线**：加载模块本身不绑定任何设备（snvme 不会自动抢绑），但第 4 步里带 `--bind` / recycle / addq / io 的测试会**接管指定 BDF 的盘**。**永远只对一块可清空的专用测试盘做这些**，别拿系统盘或有数据的盘。

cd ../test            # 即 backends/local/kernel_modules/test

- aarch64 上纯 C 测试用系统 gcc 即可，无特殊依赖。

## 第 3 步——找到测试盘的 PCI BDF

```bash
lspci -D -d ::0108                 # 列出所有 NVMe 控制器（class 0108），记下你**专用测试盘**那一行的 BDF
# 例如：0000:08:00.0
BDF=0000:08:00.0                   # ← 改成你的实际值；下面命令都用 $BDF
```
> 怎么确认哪块是"测试盘"：`lsblk`、`nvme list`（若装了 nvme-cli）对照容量/型号；**确认它没挂载、没数据**再往下。

## 第 4 步——按"安全 → 破坏性"顺序逐个跑

每个测试都是：`sudo ./<bin> $BDF`，成功末尾打印 `... all N steps passed`，失败打印 `[FAIL] step=N ... errno=E（描述）`。**严格按下面顺序**：先跑不绑定的（安全、最先该绿），再跑绑定/写盘的（破坏性、probe 是 5.10 移植的硬骨头）。

> 习惯：每个测试前 `sudo dmesg -C` 清屏，跑完 `dmesg -T | tail -N` 看内核侧日志——**用户态 `[FAIL] step=N` + 内核态 dmesg** 两边对着看，定位最快。

### ① `snvme_smoke_qgroup`（安全，**不 bind**，最先该绿）
```bash
sudo dmesg -C; sudo ./snvme_smoke_qgroup $BDF ; dmesg -T | tail -30
```
验的是：打开 `/dev/snvm_control` + 队列组 `NVM_CREATE_QUEUE_GROUP / NVM_DESTROY_QUEUE_GROUP` 生命周期 + host 内存 map。**不接管设备**，可在挂载着的机器上安全跑。
- 绿 = chrdev / ioctl / queue-group / host-map 这层在 5.10 OK。

### ② `snvme_smoke`（先安全 UAPI，再可选破坏性 `--bind`）
```bash
# 2a 安全：UAPI smoke（不接管设备）
sudo dmesg -C; sudo ./snvme_smoke $BDF ; dmesg -T | tail -30
# 2b 破坏性：完整 bring-up（会 SNVM_DEVICE_BIND 接管设备，仅对测试盘！）
sudo dmesg -C; sudo ./snvme_smoke --bind $BDF ; dmesg -T | tail -50
```
- 2a 绿 = UAPI/BAR0 mmap + host SQ/CQ 路径 OK（仍不绑定，安全）。
- 2b 是第一处**真正接管设备**的测试，会走 `pci.c` 的 bind/probe——**5.10 移植没改干净的话，最可能从这里开始挂**（见第 5 步）。

### ③ `snvme_smoke_recycle`（**bind**，admin 透传）
```bash
sudo dmesg -C; sudo ./snvme_smoke_recycle $BDF ; dmesg -T | tail -50
```
验的是：bind/probe + `NVM_RAW_ADMIN_CMD` admin 命令透传。**这是 probe 硬骨头最常暴露的地方**（bind 后 `NVM_GET_DEV_INFO` 超时 / dmesg 报 probe 错）。

### ④ `snvme_smoke_addq`（**bind**，注册用户 I/O 队列）
```bash
sudo dmesg -C; sudo ./snvme_smoke_addq $BDF ; dmesg -T | tail -50
```
验的是：B3 `NVM_ADD_USER_QUEUE` 端到端（建 I/O CQ + I/O SQ + 经 `NVM_DESTROY_QUEUE_GROUP` 级联销毁）。

### ⑤ `snvme_smoke_io`（**bind + 写盘**，全程数据校验）—— aarch64 重点
```bash
sudo dmesg -C; sudo ./snvme_smoke_io $BDF ; dmesg -T | tail -50
```
验的是：在④基础上，mmap BAR0、手搓 NVMe Read/Write SQE、敲 doorbell，并**逐 LBA 校验读写往返数据完整性**。⚠️ **会真往盘上写 LBA，目标盘必须是空的专用测试盘。**
- **aarch64 注意**：若这一步出现 **CQE 超时 / 数据偶发错**，重点查 `snvme_smoke_io.c` 里的 `mmio_writel`（doorbell 写序）——x86 用 `sfence`，arm64 走 `__atomic_thread_fence`，**arm64 上 doorbell 对设备的可见性可能需要更强 barrier（如 `dma_wmb()` 语义）**。这与内核 API 适配无关，是 arm64 内存序的后话，单列排查。

### ⑥ `snvme_smoke_gpu` —— host-only/NPU 阶段**跳过**
需要 NVIDIA + nvcc，本阶段不编不跑。等"线 B"（数据/队列上 NPU HBM、AIV 敲 doorbell）才做，且要华为开放 peer-DMA/AIV 能力。

### 便捷跑法（可选）
Makefile 提供了 `run-*` 目标和一键脚本，等价于上面：
```bash
PCI=$BDF make run-qgroup        # = sudo ./snvme_smoke_qgroup $BDF
PCI=$BDF make run               # 安全 smoke；PCI=$BDF BIND=1 make run 则加 --bind
PCI=$BDF make run-recycle / run-addq / run-io
# 或：PCI_ADDR=$BDF ./run_snvme_smoke.sh      （会自动 make + 检查 /dev/snvm_control + 选 BDF）
```

## 第 5 步——判读 & 失败排查

### 判读
- 成功：末尾 `=== snvme_smoke_xxx: all N steps passed ===`（或 `All N steps passed`）。
- 失败：看**最后一行** `[FAIL] step=N ... errno=E（描述）`；`[ OK ]` / `[WARN]` 是逐步进度，`WARN` 通常可继续。
- 用户态 step + 内核态 dmesg 对照：`errno=13(EACCES)` 多半权限/签名；`ETIMEDOUT` 多半 probe/队列没起来；`ENOMEM/EOPNOTSUPP` 在 device-mem 路径是 host-only 预期内的挡返回。

### 哪挂查哪（按测试分层）
- **① 挂** → chrdev/ioctl/queue-group/host-map 层问题：检查 `/dev/snvm_control` 是否存在、`ioctl.h` UAPI 是否和模块一致（同一棵树编的就一致）。
- **②(--bind)/③ 挂**（最常见）→ **probe/bind 硬骨头**：回 `pci.c` 看 `snvm_rebind_driver` / `nvme_probe` / `reset_work` / admin queue 初始化，对照 openEuler 5.10 自带 `drivers/nvme/host/pci.c` 的 probe 时序改。dmesg 里常见 `nvme_probe` 报错、admin 命令超时。
  - 还要确认 batch8c 的**绑定接管**生效：dmesg 应能看到 `start to bind nvme device to snvme`，且设备从 stock `nvme` 解绑、绑到 `snvme`（`driver_override=snvme` + `device_attach`）。`ls -l /sys/bus/pci/devices/$BDF/driver` 应指向 `snvme`。
- **④ 挂** → 用户 I/O 队列注册（CQ/SQ 创建、doorbell stride、队列内存）：查 `NVM_ADD_USER_QUEUE` 路径。
- **⑤ 挂** → 若前面都绿、只有 IO 往返错：优先怀疑 **aarch64 doorbell 写序**（见 ⑤ 的注意），而非内核 API。

### 通用动作
```bash
dmesg -T | tail -80                          # 内核侧最权威
cat /sys/bus/pci/devices/$BDF/driver/uevent   # 现在绑的是哪个驱动
lsmod | grep snvme                            # 模块在不在
```
卡死/盘异常时：`sudo rmmod snvme && sudo rmmod snvme_core`，必要时 `echo 1 > /sys/bus/pci/devices/$BDF/remove; echo 1 > /sys/bus/pci/rescan` 让系统盘恢复（仅在你清楚后果时）。

## 第 6 步——M1 验收判据

**①~⑤ 全绿 = M1 达成**：纯 CPU 能力阶梯（chrdev/map/queue-group → bind/probe/admin → 用户 IOQ → IO 往返校验）在 **openEuler 5.10 / aarch64** 上通过，**不依赖华为专有能力、不碰 CANN**。⑥ GPU 留到后续 NPU 阶段。

达成后建议：把每个测试的 `dmesg` + `all N steps passed` 截图/存档，记录 `uname -r`、`uname -m`、测试盘型号、driver 绑定状态，作为 M1 基线。

## 一页速查

```
0 状态   已有 snvme-core.ko + snvme.ko（5.10/aarch64，host-only）
1 加载   cd snvme-5.10-npu
         sudo insmod snvme-core.ko && sudo insmod snvme.ko
         ls -l /dev/snvm_control            # 0666 = OK
         dmesg | grep HOST-ONLY            # 看到 = host-only 生效
         卸载：sudo rmmod snvme && sudo rmmod snvme_core
2 编译   cd ../test && make                # 无 nvcc 自动跳过 _gpu
3 选盘   lspci -D -d ::0108 ; BDF=0000:08:00.0   # 专用空盘！
4 测试   每步前 sudo dmesg -C，跑完 dmesg -T | tail
         ① sudo ./snvme_smoke_qgroup $BDF        # 安全，最先绿
         ② sudo ./snvme_smoke        $BDF        # 安全 UAPI
            sudo ./snvme_smoke --bind $BDF        # 破坏性：接管设备
         ③ sudo ./snvme_smoke_recycle $BDF       # bind + admin 透传（probe 硬骨头）
         ④ sudo ./snvme_smoke_addq    $BDF       # bind + 用户 IOQ
         ⑤ sudo ./snvme_smoke_io      $BDF       # bind + 写盘 + 数据校验（arm64 看 doorbell 写序）
         ⑥ _gpu：host-only 跳过
判据     成功末尾 "all N steps passed"；失败看 "[FAIL] step=N ... errno=E"
里程碑   ①~⑤ 全绿 = M1（纯 CPU，不靠华为，不碰 CANN）
红线     --bind / recycle / addq / io 只对**可清空的专用测试盘**！
```
