## 1. 先搞清楚:这个内核模块是干什么的?(通俗版)

普通情况下,Linux 自带一个 `nvme` 驱动管理 NVMe 固态硬盘——你读写文件,数据要经过"文件系统 → 内核块层 → nvme 驱动 → 硬盘"一长串。

**SNVMe 这个模块做的是一件"绕开中间商"的事**:它让**用户态程序(将来是 GPU/NPU)直接拿到 NVMe 硬盘的队列**,自己往硬盘下读写命令、敲"门铃"(doorbell),数据在硬盘和加速卡显存之间直连,不再绕文件系统和 CPU。这就是 GPUDirect Storage 那一类"存储直连加速卡"的底座。我们要做的,是把这个底座从 NVIDIA GPU 换到华为 NPU。

**模块由两个 `.ko` 组成**(职责分两层):

| 模块 | 组成(.o) | 通俗职责 |
|---|---|---|
| **`snvme-core.ko`**(先加载) | `core.o` + `ioctl.o`(+可选 multipath/zns/hwmon) | NVMe 的"通用核心"——管理控制器/命名空间、发管理命令(Identify 等)、对用户态开一个控制入口 `/dev/snvm_control` 收 ioctl 命令 |
| **`snvme.ko`**(后加载) | `pci.o` + `map.o` + `ctrl.o` + `nvfs-pci.o` + `nvfs-p2p.o` + `list.o` | "直连加速"的主体——绑定具体的 NVMe 设备、建队列、敲门铃、把内存映射成可被硬盘 DMA 的地址 |

**各主要源文件大致作用**(只讲内核模块,不涉及项目其它代码):

| 文件 | 行数 | 干什么 |
|---|---|---|
| `pci.c` | 6228 | **最核心**。PCI 设备的探测/绑定接管、控制器复位、SQ/CQ 队列、门铃、BAR0 寄存器映射;`/dev/snvm_control` 字符设备与 ioctl 分发;"把指定硬盘从系统 nvme 手里接管过来"的逻辑都在这 |
| `core.c` | 4813 | NVMe **通用核心**:控制器/命名空间生命周期、Identify 等管理命令、磁盘与队列分配、和内核块层对接。**本次大部分内核版本差异都出在这** |
| `map.c` | 679 | **内存映射**:把 host 内存(将来是 NPU 显存)钉住、建成硬盘能 DMA 的地址,给队列和数据缓冲用 |
| `ioctl.c` | 513 | 处理用户态发来的 UAPI 命令(如透传一条 NVMe 管理命令) |
| `ctrl.c` | 167 | SNVMe 自己的"控制器对象"的引用计数/生命周期 |
| `nvfs-p2p.c` | 195 | **与 NVIDIA 打交道的那一层**(下面第 3 节重点讲) |
| `nvfs-pci.c` | 858 | SNVMe 的 PCI 辅助层(libnvm helper) |
| `list.c` | 54 | 一个小链表工具 |
| `multipath/zns/hwmon.c` | — | NVMe 的可选特性(多路径/分区命名空间/温控),按内核 CONFIG 编 |
| `fabrics/tcp/rdma.c` | — | NVMe-over-网络 的传输层,**本次本地 PCIe 直连用不到**,只是一起带着编 |

> 用户态通过 `/dev/snvm_control` 下发的命令大致有:绑定设备、建/销毁队列组、注册用户 I/O 队列、透传管理命令、映射 host/device 内存、查设备信息——这正是 [04文档](04完成编译后开始测试.md) 里 6 个 smoke 测试逐个验证的能力。

## 2. 我们的迁移思路(总体策略)

一句话:**整目录复制 5.15 公开版做基线,只在"非改不可"的地方动刀,且每处都用条件编译让它"5.10 和 5.15 都能编",改动全部带注释、可回溯。**

具体三条原则:
1. **以 openEuler 5.10 自带的 nvme 驱动当"标准答案"**。我们不靠"内核版本号猜",而是去对照华为机器上那份原生 `drivers/nvme/host/` 看 openEuler 自己怎么写,照抄。因为 openEuler 有大量自己的 backport,光看版本号会判断错。
2. **用版本守卫 `#if LINUX_VERSION_CODE < KERNEL_VERSION(5,15,0)` 包住每处改动**:5.10 走新写法,原 5.15 写法保留在 `#else`。这样**一套代码两个内核都能编**,我们也能在本地 x86+5.15 的机器上持续做"回归编译"验证没改坏。
3. **第一阶段只打通"纯 CPU + host 内存"通路**,GPU/NPU 显存那条路先不碰(见第 3 节)。

## 3. 关于 NVIDIA:那些 `nvidia_p2p_*` 关联函数怎么办?

这是迁移的第一道坎:原驱动深度依赖 NVIDIA 的 GPUDirect 接口(`nvidia_p2p_get_pages` / `dma_map_pages` / `dma_unmap_pages` 等),还要包含 NVIDIA SDK 的头 `nv-p2p.h`。**华为 NPU 服务器上根本没有 NVIDIA,这些符号和头都不存在。**

我们的处理(**"host-only 桩"策略**),分两半:

- **编译期**:NVIDIA 的头 `nv-p2p.h` 缺了会直接编不过。我们补了一份**最小桩头**,只定义代码实际用到的两个结构体类型,让它"能编过"。
- **运行期**:原代码是**运行时**才用 `__symbol_get("nvidia_p2p_xxx")` 去内核里"找"这些符号的。我们改成:**找不到就打一条 warning、继续加载,进入 HOST-ONLY 模式**(原代码是找不到就拒绝加载)。此时:
  - **host 内存路径照常工作**(纯 CPU 读写硬盘,这就是第一阶段要验的);
  - **GPU/显存直连路径**被 `nvfs-p2p.c` 的包装函数在"符号指针为空"时自动返回 `-ENOMEM`,**安全跳过、不会崩**。

打个比方:就像一个软件有个"NVIDIA 加速插件",原来没插件就拒绝启动;我们改成"没插件也能启动,只是加速功能先关着"。**将来接华为 NPU 的 peer-DMA 能力,就是把这块"插件"换成华为版本。**

## 4. 真实迁移中遇到的 bug:分类 + 怎么解决的

整个过程是"编一轮 → 报一批错 → 修一批 → 再编"地推进了 8 轮(batch1~8)。把遇到的错按**根因**归成 4 类:

### 类别 ①(最多):内核版本 API 差异(5.15 → 5.10)
内核每个版本都在改 API。5.15 上的写法,5.10 上可能**函数改了名、参数变了、或某个结构体字段干脆没了**。

| 典型报错 | 5.15 写法 | openEuler 5.10 的写法 | 怎么修 |
|---|---|---|---|
| `blk_alloc_disk` 没有 | 一把分配磁盘 | `blk_alloc_queue()`+`alloc_disk()`+手工挂 | 照 5.10 拆开写 |
| `set_capacity_and_notify` 没有 | 一个函数 | `set_capacity_revalidate_and_notify(...)` | 换名 |
| `blk_execute_rq` 签名变 | 返回状态码 | 5.10 返回 void、多一个首参 q | 改调用 |
| `part0`/`bio_set_dev`/`bi_disk` | block_device 化 | 5.10 还是老的 `bi_disk` 写法 | 一簇一起改 |
| `disk_update_readahead` | `(disk)` | `blk_queue_update_readahead(disk->queue)` | 换 API |
| `struct nvme_id_ctrl_nvm` 字段没有 | 5.15 有 | 5.10 内核头无此结构 | 5.10 分支跳过该命令 |

**解决套路统一**:版本守卫包起来,5.10 照 openEuler 原生驱动的写法重写,5.15 原写法留在 `#else`。这类占了绝大多数(core.c 11 处、multipath.c 4 处、pci.c、ioctl.c 等共约 21 处版本守卫)。

### 类别 ②:符号"声明有、但内核没导出/被裁掉"
有的函数**头文件里有声明能编过,但 openEuler 5.10 的内核没把它"导出"给模块用**,于是链接(modpost)阶段报 `undefined!`。openEuler 对这类 `EXPORT_SYMBOL_GPL` 的裁剪面比社区主线大。

- `param_set_uint_minmax`(校验队列深度)→ openEuler 5.10 没有 → 照它自带 nvme 的写法,用 `kstrtou32` 手动校验 + `param_set_uint` 替代。
- `device_driver_attach`(把指定驱动绑到指定设备)→ openEuler 5.10 **没导出** → 改用 PCI 的 `driver_override` 机制(把设备的 override 钉成 "snvme")+ 通用的 `device_attach()`,既保证只绑我们的 snvme、又避免误绑回系统自带的 nvme。

> 这里还踩了个有教育意义的坑:一开始以为只是"缺声明",补了个声明,结果编过了但链接报 undefined,才确认是"根本没导出"。**"编译期缺声明"和"链接期缺导出"是两层问题**,得用 modpost 才能区分。

### 类别 ③:头文件相关(撞名 / 作用域)
- **NVIDIA 桩头与真头撞名**:我们的桩 `nv-p2p.h` 和真实 NVIDIA 头用了不同的"防重复包含"标记,但定义了同名结构体。一旦机器上还残留真 NVIDIA 头,两份会同时展开→`redefinition`。修法:给桩头加"与真头共存"的双向守卫,无论谁先被包含都只留一份定义。
- **`struct pci_dev` 幽灵作用域**:某头文件第一次用到 `struct pci_dev` 时没提前声明它,C 语言会把它当成一个"局部幽灵类型",和真正的 `struct pci_dev` 不是一回事→报 `conflicting types` / `incompatible pointer type`。修法:在用它之前加一行前置声明 `struct pci_dev;`。(本机 5.15 因为包含顺序不同,碰巧没暴露,5.10 才报——典型的"潜伏 bug 被新环境照出来"。)

### 类别 ④:架构专属头(x86 → aarch64)
`pci.c` 里 `#include "asm/string_64.h"`——这是 **x86_64 专属**的头,aarch64 根本没有。修法:换成架构中立的 `<linux/string.h>`(memcpy/memset 等它都提供,全平台通用)。

## 5. 重要认识:x86 和 aarch64 到底差多少?"能编译"意味着什么?

这是我(作为新手)一开始的疑问,也想在组会上说清楚,**避免误判**:

**❶ "能编译通过" ≠ "x86 和 aarch64 差不多"。** 把上面 4 类 bug 数一数:**约 95% 是"内核版本差异"(类别①②),只有 1 个(类别④的 string_64.h)是真正的"架构差异"。** 也就是说,我们这一周主要在跨"5.15→5.10 内核版本"这道坎,而不是跨"x86→arm64 架构"那道坎。所以"编过了"主要证明的是**版本移植**做对了,**不能**据此推断两个架构没差别。

**❷ 架构真正的差异,编译器看不出来,它藏在"运行期"。** x86 和 aarch64 最要命的区别是**内存序(memory ordering)和缓存一致性**:
- x86 内存序强,写完内存基本就"立刻可见";
- **aarch64 内存序弱**,需要程序员显式插"屏障(barrier)"来保证顺序。

我们这个驱动恰恰有个最敏感的点:**敲门铃(doorbell)**——必须保证"队列里的命令内容"先写进去、**再**通知硬盘"有新命令了"。x86 用 `sfence` 保证,arm64 走的是另一套屏障。**如果 arm64 上这个顺序没保证好,硬盘可能读到一条"半成品命令",轻则超时、重则写到错误的位置。这类问题编译期 100% 看不出来,只有真机跑 IO 才会暴露。**

**结论:两个架构差别是实质性的,但差别集中在运行期(尤其 doorbell/DMA 的内存序),这正是为什么"编过了"之后必须认真测试。**

## 6. 下一步怎么干:用"测试结果"驱动

**❶ 现在的真实状态(诚实说):** 我们这周的策略本质是**"想办法让它编过 + 能加载"**,并**刻意没有改动 IO/队列的核心逻辑**(只改了它周围的 API 适配)。所以:
- **已证明**:能编、能加载、host-only 模式在 API 层面通(安全测试那几个)。
- **还没证明**:在真机 5.10/aarch64 上,绑定/探测/队列/真实读写到底对不对。
- 所以**后面测试大概率会遇到不少问题**,这是预期之内的,不是翻车。

**❷ 测试失败时,怎么判断"是代码写错了"还是"特性不支持"?** 这是后续工作的核心方法。每个测试失败时,看 **用户态 `[FAIL] step=N` + 内核 `dmesg` 日志**,定位到是哪一层,然后判型:

| 失败属于 | 特征 | 怎么处理 |
|---|---|---|
| **(A) 代码 bug**(我们移植引入或照出来的) | 某个 API 映射错、字段偏移假设错、**arm64 doorbell 内存序**、PRP/地址算错 | 读代码 + 对照 openEuler 原生 nvme 驱动,改对它 |
| **(B) 特性/平台不支持**(不是 bug,是边界) | 走到 GPU/显存直连这类 **host-only 故意关掉**的路;或某硬件 quirk | 不是"修",而是确认这是当前阶段的**范围边界**,记录并推迟 |

**判型流程**(后续每轮测试都这么走):
```
跑测试 → 看 [FAIL] step=N + dmesg
   → 落在哪一层?(chrdev/ioctl / 绑定probe / 队列 / 真实IO)
        → 该层是 host-only 故意关的 device 路径?  → (B) 边界,记录推迟
        → 否则,对照 openEuler 5.10 原生写法看逻辑  → (A) 改代码,再测
```

按 [04文档](04完成编译后开始测试.md) 的顺序,最可能先在 **③ recycle(绑定+探测)** 这块"硬骨头"卡住(probe 时序),以及 **⑤ io(真实读写)** 的 arm64 doorbell。这两处会是下周的主战场。

**❸ 里程碑:** [04文档](04完成编译后开始测试.md) 里 6 个 smoke 测试的 ①~⑤ 全绿 = **M1**(纯 CPU 能力阶梯在 openEuler/aarch64 上通过,不依赖华为专有能力、不碰 CANN)。⑥ GPU/显存路径留到 M1 之后、且要华为开放 peer-DMA 能力才做。

## 7. 一句话风险与数据安全(组会可能会问)

- **加载模块本身零风险**:`insmod` 只建一个控制入口,不绑定、不碰任何硬盘。
- **带绑定/写盘的测试是"按设计就会破坏数据"的**:它会接管指定硬盘、并直接覆写裸扇区(io 测试从 10 GiB 处写)。**铁律:只对一块可清空的专用测试盘跑,绝不碰系统盘/有数据的盘。**
- 详细的风险来源分析见前一轮讨论(模块只接管你指定的那一个设备,不波及其它盘;控制器复位不擦数据,真正写数据的是 io 测试那条显式路径)。
