## 0. 先回答你的问题：这一层和 CANN 有关系吗？

**没有关系。** 这一层是**内核 NVMe 驱动**（SNVMe 内核模块，`.ko`），跑在内核态，干的是"绑定 NVMe、建队列、敲 doorbell、收发数据"。

CANN（AscendCL / Ascend C）是**用户态的 NPU 计算运行时**，要等到"线 B"——把数据缓冲/队列搬上 NPU HBM、让 AIV 核敲 doorbell——而且是用户态那条线（仓库里 `Geminifs/ascend_cann_port/` 是它的工作区）才会用到。

> 本次做的（①~⑤ 纯 CPU + host 内存 + 内核驱动 bring-up）：**从头到尾不碰 CANN，也不需要装 CANN。** 只需要：openEuler 内核头（kernel-devel）+ gcc/make + 一块可清空的 NVMe 测试盘。

## 1. 我替你建好的目录是什么

```
Geminifs_smoke/backends/local/kernel_modules/snvme-5.10-npu/
```
它是 **`snvme-5.15.0-public`（B3 模块）的完整副本**，外加我做的 **host-only 改造**，目的是让它在**没有 NVIDIA 的机器上也能编译、能加载**。

相对原始 5.15 基线，我**只动了 3 个地方**（其余 23 个文件逐字节不变，方便你将来对照）：

| 文件 | 动作 | 为什么 |
|---|---|---|
| `pci.c` | **改 1 处**（模块初始化 `nvme_init`） | 原代码找不到 `nvidia_p2p_*` 符号就 `-EOPNOTSUPP` 拒绝加载；改成失败时打 warning、继续进 host-only 模式 |
| `nv-p2p.h` | **新增**（host-only 桩头） | 原 `nvfs-p2p.c`/`map.c` 要 `#include "nv-p2p.h"`（NVIDIA SDK 的头），NPU 服务器没有，会编译失败。补一份最小桩头让它编过 |
| `Makefile` | **新增**（独立编译入口） | 原 `Makefile.in` 有 CMake 占位符；新增一个不依赖 CMake、`make` 就能编的版本 |

> 这 3 处改动都是**与内核版本无关**的（host-only / 编译脚手架），所以可以由我离线先做好。

### 我已经验证到什么程度（重要、诚实说明）

✅ **我在本机（恰好也是 5.15 内核）用 `make` 编译了 `snvme-5.10-npu`，`snvme-core.ko` 和 `snvme.ko` 都成功产出、零报错。**
这证明：(1) 桩头 `nv-p2p.h` 够用、能在无 NVIDIA 下编过；(2) `pci.c` 的 host-only 改动语法正确；(3) `Makefile` 能用。

⚠️ **但这是对着 5.15 头编的，不等于在 openEuler 5.10 上能直接编过。**
5.15 → 5.10 之间内核 API 有差异（见第 3 步），这部分**我无法离线替你改**——必须对着你服务器上**真实的 5.10 内核头**按编译报错改，盲改只会帮倒忙。所以：**这个目录帮你跨过了"NVIDIA/host-only"这道坎，剩下的是"5.10 内核 API 适配"那道坎，要在服务器上做。**

> 我已经把本地编译产物（`*.ko/*.o` 等）清理掉了，目录里只有源码 + 我加的 3 个文件，干净可拷。

## 3. 第 2 步——编译，按报错修 5.10 API（这是你明天的主要工作）

```bash
cd Geminifs_smoke/backends/local/kernel_modules/snvme-5.10-npu
make 2>&1 | tee build.log
```

会出现两种情况：

**情况 A：直接编过（运气好，openEuler backport 够多）**
→ 出现 `snvme-core.ko` 和 `snvme.ko`，直接跳到第 4 步。

**情况 B：报一批 5.15→5.10 的内核 API 错（更可能）**
→ **逐个按报错改**。方法（比清单更重要）：
1. 看报错说**哪个函数/字段"未声明 / 不是成员 / 参数不对"**。
2. 去服务器上你已有的那份原生驱动 `kernel-openEuler-22.03-LTS-drivers-nvme/drivers/nvme/host/` 里 `grep` 这个名字，看 **5.10 里它叫什么、签名是什么、字段在不在**。
3. 照 5.10 的写法把 `snvme-5.10-npu/` 里对应的地方改过来，**每改一处加一行注释**：
   ```c
   /* [SNVME-NPU 迁移修改] 5.15→5.10：xxx 在 5.10 里是 yyy，原因…… */
   ```

**可能（不一定全中，以编译器实际报错为准）遇到的高频差异：**

| 报错关键字 | 5.15 写法 | openEuler 5.10 大概率写法 | 主要出现在 |
|---|---|---|---|
| `blk_mq_alloc_disk` 未声明 | `blk_mq_alloc_disk()` | `alloc_disk()` + `blk_mq_init_queue()` + `device_add_disk()`（5.14 才合并成一个） | `core.c` |
| `set_capacity_and_notify` 未声明 | `set_capacity_and_notify()` | `set_capacity()` + `revalidate_disk_size()` | `core.c` |
| `nvme_init_ctrl_finish` 未声明 | `nvme_init_ctrl_finish()` | `nvme_init_identify()`（`snvme-rename.sed` 注释也提过） | `core.c`/`pci.c` |
| `BIO_MAX_VECS` 未声明 | `BIO_MAX_VECS` | `BIO_MAX_PAGES`（5.12 改名） | 各处 |
| `struct nvme_ctrl`/`nvme_dev` 某字段不存在 | 5.15 的字段 | 对照 5.10 `nvme.h` 改名/删 | `pci.c`/`core.c` |

> **改不动、看不懂某处"5.15 为什么这么写"时**，才对那一个文件做三方 diff（拿原生 5.15 的 `drivers/nvme/host/同名文件` 和 `snvme-5.15.0-public/同名文件` 对比，看 SNVMe 到底改了哪几处），把那几处看懂再套到 5.10。**不要一上来就全文件三方合并**——大多数错照着报错改就行。
>
> **备选方案**：openEuler 5.10 夹在仓库的 5.4 和 5.15 两个 baseline 中间，而 `blk_mq_alloc_disk` 这类磁盘分配大改是 5.14 才进的。**如果 5.15 起手报了一大堆磁盘分配/probe 相关的错，可以改用 `snvme-5.4.241-1-tlinux4-0017` 作为起点**（它也实现了完整 B3），它的 nvme 内核内部可能更接近 5.10。换 baseline 时，把我对 `snvme-5.10-npu` 做的同样 3 处 host-only 改动照搬过去即可（见第 6 节"我的改动清单"）。

**判读 + 哪挂查哪**（详见 `01…md` 第 2 节、`02…md` 第 0 节的能力表）：
- 成功末尾打印 `all N steps passed`；失败看**最后一行 `[FAIL] step=N`**。

## 6. 我对 `snvme-5.10-npu` 的改动清单（精确，便于复查/回退/换 baseline 时照搬）

### 改动 #1：`pci.c` — 模块初始化进 host-only
位置：`nvme_init()`（原 5.15 基线约 6066 行）。
```c
/* 原始： */
if(nvfs_nvidia_p2p_init()) {
    printk("Could not load nvidia_p2p* symbols\n");
    ret = -EOPNOTSUPP;
    return ret;
}
/* 改成（带 [SNVME-NPU 迁移修改 #1] 注释块）： */
if(nvfs_nvidia_p2p_init()) {
    printk(KERN_WARNING "snvme: nvidia_p2p* symbols not found; "
           "running in HOST-ONLY mode "
           "(device-memory ioctls will return -ENOMEM/-EOPNOTSUPP)\n");
    /* 不再 return；继续加载 */
}
```
原因：没有 NVIDIA 时也能加载，host 内存路径照常工作；GPU/device 路径由 `nvfs-p2p.c` 的包装函数在指针为 NULL 时自动返回 `-ENOMEM`（已确认不会崩）。

### 改动 #2：新增 `nv-p2p.h`（host-only 桩头）
原因：`nvfs-p2p.c`/`nvfs-p2p.h`/`map.c` 都 `#include "nv-p2p.h"`，缺它编译失败。桩头只定义代码实际用到的两个类型：
- `struct nvidia_p2p_page_table { u32 entries; }`（map.c 读 `->entries`）
- `struct nvidia_p2p_dma_mapping { u64 *dma_addresses; }`（map.c 读 `->dma_addresses[i]`）
+ 两个 `_t` typedef。host-only 运行时根本走不到读这些字段的 device 路径，字段只为编译存在。

### 改动 #3：新增 `Makefile`（独立编译入口）
原因：绕开 `Makefile.in` 的 CMake 占位符，`make` 直接编。对象集与原始一致；`-I` 指向 UAPI 头和本目录。

> **换用 5.4 baseline 时**：把这 3 处同样套到 `snvme-5.4.241` 的副本上即可（pci.c 的初始化处函数名/行号可能不同，但逻辑一样：找不到 nvidia 符号别 return，继续加载）。

### 一句话验证我没乱改
```bash
cd backends/local/kernel_modules
diff -rq snvme-5.15.0-public snvme-5.10-npu
# host-only 批次（第 1~6 节）：Makefile / nv-p2p.h 新增 + pci.c differ
# 叠加 5.10 API 批次（第 8 节）后：还会多出 core.c / multipath.c differ
```

## 8.【进度更新 2026-06-05】5.10 内核 API 适配（已替你修一批）

> 你已在华为服务器上确认：`uname -r=5.10.0`、`uname -m=aarch64`，并 `make` 出现一批 5.15→5.10 的内核 API 报错。**我已用 openEuler 5.10 自带的 nvme 驱动作权威参照，把这批改好了**，并保证本机 5.15 仍能编过（回归验证）。你 pull 后重新 `make` 即可继续。

### 8.1 方法论（很关键）：用 openEuler 自带 nvme 驱动当"标准答案"
我没有凭内核版本号猜，而是对每个报错符号，去你机器上那份 `kernel-openEuler-22.03-LTS-drivers-nvme/drivers/nvme/host/` 看 **openEuler 5.10 自己怎么写**，照抄。这避免两类坑：
- **openEuler 有 backport**：`blk_mq_alloc_disk`、`blk_cleanup_disk` 本是 5.14/5.15 才有的，**openEuler 5.10 已 backport**（它自己 nvme 驱动在用），所以这两处 snvme 代码**不用改**——也解释了你为何没报这两个错。
- **openEuler 没 backport**：`blk_alloc_disk`、`set_capacity_and_notify`、`bvec_virt`、`disk_live`、`struct nvme_id_ctrl_nvm`、`max_zeroes_sectors` 字段等，5.10 确实没有，必须改。

所有改动都用 `#if LINUX_VERSION_CODE < KERNEL_VERSION(5,15,0)` 条件编译包裹：**openEuler 5.10 走新写法，原 5.15 代码保留在 `#else`**。这样代码**同时能在 5.10 和 5.15 上编译**，我也能用本机 5.15 持续回归。

### 8.2 本批改动清单（3 个文件，均带 `[SNVME-NPU]` 注释）

| 报错符号 | 文件:位置 | 5.10 改法（依据 openEuler 5.10） |
|---|---|---|
| `set_capacity_and_notify` | core.c:138 / 1847 | → `set_capacity_revalidate_and_notify(disk, size, false)` |
| `blk_mq_set_request_complete` | core.c:393 | → 内联 `WRITE_ONCE(req->state, MQ_RQ_COMPLETE)`（该辅助 5.13+ 的实现本体） |
| `bvec_virt` | core.c:974 | → `page_address(bv_page) + bv_offset` |
| `blk_execute_rq`（返回值+签名） | core.c:1050 | 5.10：`blk_execute_rq(q, disk, rq, at_head)` 返回 void，状态从 `nvme_req(rq)` 读 |
| `blk_execute_rq_nowait`（签名） | core.c:1277 / pci.c:1485 / pci.c:2710 | 5.10 多首参 q：`blk_execute_rq_nowait(rq->q, NULL, rq, at_head, done)` |
| `disk_live` | core.c:1860 | → `(disk->flags & GENHD_FL_UP)` |
| `nvme_id_ctrl_nvm` + `max_zeroes_sectors` | core.c:2866 / 4620 / 1851 | 5.10 内核头无此结构体、`struct nvme_ctrl` 无此字段；5.10 分支只按 ONCS 设 discard 上限、跳过 NVM 命令集 Identify，BUILD_BUG_ON 仅 5.15+ 校验，write-zeroes 上限置 0 |
| `blk_alloc_disk`（**主动发现**） | multipath.c:456 | 5.10 无此 API：按 openEuler 用 `blk_alloc_queue()`+`alloc_disk(0)`+手工挂 queue；保留命名 `snvme%dn%d`，不设 5.13 才有的 QUEUE_FLAG_NOWAIT |
| `device_add_disk`（**主动发现**，返回值） | core.c:3897 | openEuler 5.10 该函数返回 void（带返回值的叫 device_add_disk_safe）；5.10 分支直接调用不判返回，用 `if(0) goto` 保住清理标签避免 -Wunused-label |

> `blk_cleanup_disk`（core.c:3922、multipath.c:848）**不动**——openEuler 5.10 已 backport，可直接用。
> 另在 core.c / pci.c / multipath.c 顶部各加了 `#include <linux/version.h>`。守卫数量：core.c 12、pci.c 2、multipath.c 1。

### 8.3 验证程度
✅ 本机（5.15.0）`make` **零报错**编出两个 .ko——证明所有 `#else`（原 5.15）分支完好、所有 `#if` 守卫语法正确。

### 8.4 你接下来怎么做（内核移植是"一波波"的）
报错常分多轮：修好一批、往下走又暴露下一批。流程：
1. **我 commit → 你（开发机）push → NPU 服务器 pull**：
