## 0. 先建立直觉：这 6 个测试到底在测什么

GeminiFS 的核心诉求是：**让加速器（GPU / 未来的 NPU）绕过 CPU，直接和 NVMe SSD 通过 DMA 收发数据**。要做到这点，需要打通一条链路：

```
加速器/CPU 分配 SQ/CQ 队列内存
   → 把队列内存地址转成 NVMe 能用的 DMA 地址
   → 用 NVMe admin 命令把这对队列注册成合法的 I/O queue
   → mmap BAR0，让加速器/CPU 能直接敲 doorbell
   → 自己写 SQE、敲 doorbell、轮询 CQE，完成读写
```

这条链路很长，任何一环都可能在新平台（华为 NPU）上断掉。所以仇博把它**拆成了 6 个独立的冒烟测试（smoke test）**，从「最安全、只测 API」一路爬到「最完整、GPU 自己敲 doorbell」。**这正是我们迁移到 NPU 时应该照搬的「能力阶梯」**：一级一级验证，断在哪一级就知道缺什么能力，再去找华为对接。

| 测试程序 | 验证的能力 | 是否绑定控制器 | 是否破坏盘上数据 | 是否需要 GPU/CUDA |
|---|---|---|---|---|
| `snvme_smoke` | 基础 UAPI：字符设备、BAR0 mmap、host 内存映射 | 默认否（`--bind` 是） | 默认否 | 否 |
| `snvme_smoke_qgroup` | 队列组（queue group）容器的生命周期 | **否** | 否 | 否 |
| `snvme_smoke_recycle` | admin 命令透传（`NVM_RAW_ADMIN_CMD`） | **是** | 否（不写盘，但抢设备） | 否 |
| `snvme_smoke_addq` | host 内存的 SQ/CQ **注册成 NVMe I/O queue** | **是** | 否（不发读写） | 否 |
| `snvme_smoke_io` | **CPU 全程**写 SQE+敲 doorbell+轮询，真实读写校验 | **是** | **是（写盘）** | 否 |
| `snvme_smoke_gpu` | **GPU 全程**：队列+数据+doorbell 都在 GPU 上 | **是** | **是（写盘）** | **是** |

> 名词速查（新手必看）：
> - **SQ / CQ**：Submission Queue（提交队列，放命令）/ Completion Queue（完成队列，放回执）。一对 SQ+CQ 就是一条 NVMe I/O 通道。
> - **SQE / CQE**：队列里的一格。SQE = 64 字节的「命令单」；CQE = 16 字节的「回执」。
> - **doorbell**：BAR0 里的一个寄存器。你往 SQ ring 写好命令后，写一下 doorbell 告诉控制器「我放了新命令到第几格」，控制器才会去取。
> - **BAR0**：PCIe 设备的一段寄存器内存窗口（Base Address Register 0）。NVMe 的 CAP 寄存器、doorbell 都在这里。`mmap` 它就能让用户态/加速器直接读写这些寄存器。
> - **ioctl**：用户态程序对内核字符设备「下命令」的标准方式。SNVMe 的所有控制操作都是 ioctl。
> - **bind（绑定）**：把 NVMe 设备从系统自带的 `nvme` 驱动「夺过来」交给 `snvme` 驱动管。绑定后系统原来的 `/dev/nvmeXnY` 会消失，换成 `/dev/snvmeXnY`。
> - **PRP / PRP List / SGL**：告诉 NVMe「数据缓冲区在哪」的三种地址描述方式。小数据用 PRP1(+PRP2)，大数据用 PRP List 或 SGL。

## 1. 公共结构（6 个文件都长一个样的部分）

这 6 个程序是「同一个模板的不同深度版本」，理解一个就理解全部。它们都包含这套**公共骨架**（我已在每个文件里逐函数加了中文注释）：

- `step_ok() / step_warn() / step_fail()`：统一的日志函数。每完成一步就打印 `[ OK ] step=N ...`；失败就打印 `[FAIL] step=N ... errno=...` 并**立即退出（exit code 2）**。所以看输出时，**最后一行是 `[FAIL]` 的那一步，就是断点**。
- `parse_bdf()`：把命令行参数 `"0000:08:00.0"` 解析成 PCI 地址结构体（域:总线:设备.功能，即 Domain:Bus:Device.Function，简称 BDF）。
- `do_ioctl()`：对 `ioctl()` 的薄封装，失败时自动打印是哪个 ioctl 出错。
- `usage()`：打印用法。
- `main()`：把上面这些串成完整流程。**真正的测试逻辑全在 `main()` 里**，按 `[1] [2] …` 或 `Phase 0/1/2…` 分阶段。

> 阅读建议：先读文件**顶部的大段英文注释**（每个文件开头都写清了这个测试「测什么、为什么、危险吗」），再读 `main()` 上方我加的中文流程概述，最后对着 `[N]` 步骤往下看。

## 2. 逐个测试详解：测什么 + 怎么跑 + 步骤拆解

### 2.0 通用前置条件（跑任何测试前都要满足）

1. **加载内核模块**，并出现控制字符设备：
   ```bash
   sudo insmod /path/to/snvme-core.ko
   sudo insmod /path/to/snvme.ko
   ls -l /dev/snvm_control      # 必须存在，权限一般是 0666
   ```
   > ⚠️ 当前代码在 NPU 服务器上**大概率卡在这一步**：`snvme.ko` 初始化时强制调用 `nvfs_nvidia_p2p_init()`，找不到 `nvidia_p2p_*` 符号就返回 `-EOPNOTSUPP`。这正是第 3 节迁移计划要先解决的「host-only 模式」问题。

2. **找到目标 NVMe 的 BDF**：
   ```bash
   lspci -D -d ::0108              # 列出所有 NVMe 控制器，形如 0000:08:00.0
   ```

3. **编译测试**：
   ```bash
   cd Geminifs_smoke/backends/local/kernel_modules/test
   make                            # 没有 nvcc 时会自动跳过 snvme_smoke_gpu，其余照常编译
   ```
   编译只依赖一个 UAPI 头：`../../nvme/libnvm/include/ioctl.h`。**纯 C，不需要 CUDA**（除了 GPU 版）。

4. **每轮测试前后存一份内核日志**，方便定位：
   ```bash
   sudo dmesg -T > /tmp/dmesg-before.txt
   # ... 跑测试 ...
   sudo dmesg -T > /tmp/dmesg-after.txt
   diff /tmp/dmesg-before.txt /tmp/dmesg-after.txt
   ```

> **危险等级提醒**：带「写盘 / bind」的测试**只能在一块可以清空的专用测试盘上跑**，绝不能在挂着文件系统、有数据的生产盘上跑。bind 会把设备从系统驱动夺走；写盘会覆盖 LBA。

### 2.1 `snvme_smoke` —— 地基：字符设备 + BAR0 + host 映射

**测什么**：所有**不触发 NVMe 控制器 probe** 的内核↔用户入口。是最安全的入门测试。

**两种模式**：
- 默认（UAPI-smoke，**安全**）：即使设备正被系统 `nvme` 驱动占用也能跑，因为它不碰数据通路。
- `--bind`（完整 bring-up，**破坏性**）：会真正绑定控制器、等 `/dev/snvmeXnY` 出现、`pread` 512 字节、再解绑。

**怎么跑**：
```bash
# 安全：只测 API
sudo ./snvme_smoke 0000:08:00.0

# 破坏性：完整绑定 + 读一次
sudo ./snvme_smoke --bind 0000:08:00.0
```

**步骤拆解**（`main()` 里的 `[1]`~`[9]` 与 `[F1]`~`[F3]`，`--bind` 时多 `[B1]`~`[B4]`）：

| 步骤 | 动作 | 验证点 |
|---|---|---|
| [1] | `open(/dev/snvm_control)` | 字符设备工厂存在 |
| [2] | `SNVM_CHRDEV_CREATE(BDF)` | 创建 per-controller 字符设备，内核回写 minor 号 |
| [3] | `open(/dev/ssnvme<minor>)` | per-controller 字符设备可用 |
| [4] | `mmap(BAR0, 8KiB)` | BAR0 能映射到用户态 |
| [5] | 读 BAR0 的 CAP 寄存器 | 寄存器解码符合 NVMe 规范（全 0 = BAR 没映射上，是真 bug；全 F = 控制器掉电，仅告警） |
| [6] | `NVM_SET_IOQ_NUM(2)` | 设置用户侧 IOQ 数量状态 |
| [7][8] | `mmap` 两页 + `NVM_MAP_HOST_MEMORY` 映射 SQ/CQ 环 | host 内存能 pin 住并拿到 DMA 地址 |
| [9] | `NVM_SET_SHARE_REG(1)` | 打开共享寄存器开关 |
| [B1]~[B4] | bind → `NVM_GET_DEV_INFO` 轮询 → 打开块设备 `pread` 512B → unbind | 完整 probe 跑通、块设备出现可读 |
| [F1]~[F3] | 反向清理：unmap → munmap+close → `SNVM_CHRDEV_REMOVE` | 状态机能干净复位 |

**成功标志**：最后打印 `All N steps passed. SNVMe is healthy ...`。

---

### 2.2 `snvme_smoke_qgroup` —— 队列组容器的生命周期（不绑定，最安全的破坏前测试）

**测什么**：B1/B2 引入的「每个 fd 一个 queue group 容器」的纯生命周期管理。**它不 bind 控制器**，所以挂着盘也能安全跑——队列组的创建/销毁设计上与 bind 无关。

**怎么跑**：
```bash
sudo ./snvme_smoke_qgroup 0000:08:00.0
```

**步骤拆解**（`[1]`~`[19]`，分两大块）：
- **B1（容器生命周期，步骤 1~10）**：创建 group 拿到非 0 的 `group_id`；同一 fd 第二次创建应被 `-EBUSY` 拒绝（每 fd 上限 = `NVM_MAX_GROUPS_PER_FD`）；正常销毁；重复销毁应 `-ENOENT`；`group_id=0` 应 `-EINVAL`；**跨 fd 隔离**（fd A 不能销毁 fd B 的 group，应 `-ENOENT`）；关闭 fd 时内核**级联回收**孤儿 group；`flags` 非零应 `-EINVAL`。
- **B2（带 group_id 的内存映射，步骤 11~19）**：`NVM_MAP_HOST_MEMORY` 新模式（指定 `group_id`）把一页 host 内存注册进 group；非法 group_id → `-ENOENT`；`reserved` 字段非零 → `-EINVAL`；跨 fd 注册 → `-ENOENT`；销毁 group 时**级联 drain** 已注册的 map（销毁后再 unmap 应 `-EINVAL`，证明确实被回收了）。

**成功标志**：`=== snvme_smoke_qgroup: all N steps passed ===`。
**额外验证**：`dmesg` 里可看到 `NVM_CREATE_QUEUE_GROUP id=...`、`cascade-destroyed K orphan group(s)`、`destroy_qgroup id=N drained 1 map` 等内核日志。

---

### 2.3 `snvme_smoke_recycle` —— admin 命令透传

**测什么**：`NVM_RAW_ADMIN_CMD` —— 让用户态把任意 NVMe admin 命令塞进控制器自有的 admin queue，并把 CQE 的 status/DW0/DW1 原样透传回来。这是 NVMeService 做「队列回收」（Delete/Create I/O SQ/CQ）的底层积木。**会 bind（破坏性，但不写盘）**。

**怎么跑**：
```bash
sudo ./snvme_smoke_recycle 0000:08:00.0
```

**步骤拆解**（`[1]`~`[8]`）：
- `[1]~[3]` 建字符设备；
- `[4]` **未绑定时**发 admin 命令应 `-ENODEV`（防止内核在没绑定时解引用空指针 oops，是重要的负向测试）；
- `[5][6]` bind + 轮询 `NVM_GET_DEV_INFO` 等 probe 完成；
- `[7a]` **正向**：发 Identify Controller（无数据缓冲），证明 SQE→CQE 能往返；
- `[7b]` **负向**：发保留 opcode `0xFF`，控制器必须以 `SC=0x01 (Invalid Command Opcode)` 拒绝——证明失败状态也能如实透传回来；
- `[8]+[F]` unbind、清理。

**成功标志**：`=== snvme_smoke_recycle: all N steps passed ===`，且 `[7b]` 报告 `SC=0x01`。

---

### 2.4 `snvme_smoke_addq` —— host 的 SQ/CQ 注册成 NVMe I/O queue（B3，**不发 IO**）

**测什么**：`NVM_ADD_USER_QUEUE` 的端到端。在**已绑定**的控制器上，把用户提供的 host 内存 SQ/CQ 通过 Create I/O CQ + Create I/O SQ admin 命令注册成合法 I/O queue，并拿回 doorbell 偏移。**故意不发任何读写、不敲 doorbell**——只验证「注册」这一步。这正好对应你说的「能力阶梯第二步」。

**怎么跑**：
```bash
sudo ./snvme_smoke_addq 0000:08:00.0
```

**步骤拆解**（`Phase 0`~`Phase 10`）：
- `Phase 0/1`：建字符设备、bind **前**创建 group；
- `[4]` **未绑定时** `NVM_ADD_USER_QUEUE` 应 `-ENODEV`；
- `[4b]` `NVM_SET_KERNEL_IOQ_CAP(36)`：限制内核侧 IOQ 数量，**给用户队列池留出 QID**（否则在 192 核机器上内核会把控制器给的 QID 全占光，用户队列建不出来，报 `SC=0x4101`）；
- `Phase 2/3`：bind + `NVM_GET_DEV_INFO`，校验新版字段 `q_depth / max_user_qid / bar0_size / max_queues_per_group` 合理；
- `Phase 4/5`：分配**页对齐**的 SQ/CQ 环（SQ=q_depth×64B，CQ=q_depth×16B，必须单页放得下），`NVM_MAP_HOST_MEMORY` 注册进 group；
- `Phase 6`：`NVM_ADD_USER_QUEUE` 建 2 条队列，检查返回的 doorbell 偏移非 0；
- `Phase 7`：**负向**——超过 `max_queues_per_group` 应 `-EBUSY`；
- `Phase 8`：销毁 group，**级联** Delete I/O SQ/CQ + 回收 QID + drain map；
- `Phase 9`：对已销毁 group 再 add 应 `-ENOENT`；
- `Phase 10`：unbind、清理。

**成功标志**：`=== snvme_smoke_addq: all N steps passed ===`，并打印每条队列的 `qid / sq_db / cq_db`。

---

### 2.5 `snvme_smoke_io` —— CPU 全程真实读写（能力阶梯第三步，最关键的 CPU 基准）

**测什么**：在 `addq` 建好的用户队列上，**CPU 亲手**构造 SQE → 写 SQ ring → 敲 BAR0 doorbell → 轮询 CQ ring 的 phase bit → 校验数据。队列和数据缓冲都在 **host 内存**。**会写盘（破坏性，从 LBA 2621440 = 10GiB/4KiB 起）**。

> 这是迁移路上最重要的「纯 CPU 基准线」：只要它在 NPU 服务器上跑通，就证明 **SNVMe 内核侧的数据通路在新内核上完全可用**，后续所有 NPU 相关失败都可以归因到「NPU 内存/doorbell 能力」而不是「SNVMe 本身」。

**怎么跑**：
```bash
sudo ./snvme_smoke_io 0000:08:00.0
```

**步骤拆解**（`Phase 0`~`Phase 8`，重点在 Phase 5 系列）：
- `Phase 0~3`：建字符设备、建 group、限 IOQ、bind、取 dev info、分配并注册 SQ/CQ 环和数据缓冲、`NVM_ADD_USER_QUEUE`、`mmap BAR0`、构造每条队列的运行时状态（`test_queue`：sq_tail/cq_head/cq_phase/doorbell 指针）；
- `Phase 5`：**PRP1，4KiB** 单页 IO ×16，一条队列写、另一条队列读回，逐字节校验（字节模式里编码了 qid 和迭代号，能定位串扰）；
- `Phase 5b`：**PRP1+PRP2，8KiB** 跨两页（验证双 PRP 寻址、页不串位）；
- `Phase 5c`：**PRP1+PRP List，16KiB** 四页（验证 PRP List 页寻址）；
- `Phase 5d`：**SGL Data Block**（仅当控制器在 Identify 里声明支持 SGL 时才跑）；
- `Phase 6`：**SQ tail 回绕**压力测试（发 q_depth+8 次，强制 sq_tail 绕一圈、cq_phase 翻转）；
- `Phase 7`：**B6 验证**——数据缓冲用 `map_kind=DATA + group_id=0` 注册，销毁 group 后数据缓冲仍存活，重建 group + 重新 add 队列，用**同一批数据缓冲**再做一次写读校验；
- `Phase 8`：munmap BAR0、销毁 group、unbind、清理。

**成功标志**：`=== snvme_smoke_io: all N steps passed ===`。
**关键实现细节**：`mmio_writel()` 在 x86 上**先 `sfence` 再写 doorbell**，保证「SQE 内容先于 doorbell 对设备可见」。这条排序语义在迁移到别的架构（如 aarch64）或 NPU 时**必须有等价物**，否则控制器会读到半成品 SQE。

---

### 2.6 `snvme_smoke_gpu` —— GPU 全程（能力阶梯第四~六步的 NVIDIA 完整版）

**测什么**：和 `snvme_smoke_io` 同样的相位/分层覆盖，但**全部搬到 GPU**：
- SQ/CQ 环：`cudaMalloc` 在显存，用 `NVM_MAP_DEVICE_MEMORY`（走 NVIDIA p2p）注册；
- 数据缓冲：同上，在显存；
- doorbell：BAR0 先 CPU `mmap`，再 `cudaHostRegister(..., cudaHostRegisterIoMemory)` + `cudaHostGetDevicePointer` 翻译成 GPU 能访问的地址；
- **提交 SQE / 敲 doorbell / 轮询 CQE 全部由 CUDA 核函数完成**（`k_submit_rw` 里 `__threadfence_system()` 后写 SQ doorbell；`k_poll_one` 轮询 phase bit 后写 CQ doorbell）；
- `--rounds N`：动态分配/释放循环，验证 QID 池回收和 p2p `get_pages/put_pages` 引用计数不泄漏。

**前置条件**：必须加载 NVIDIA 驱动且 `nvfs_nvidia_p2p_init()` 成功，否则 snvme 根本不让加载。**会写盘（破坏性）**。

**怎么跑**：
```bash
make snvme_smoke_gpu                                  # 需要 nvcc
sudo ./snvme_smoke_gpu --gpu 0 --rounds 4 0000:08:00.0
```

> **这个文件是 NPU 迁移的「目标蓝图 + 缺口清单」**。它把 NVIDIA 专有能力用了个遍，每个用到的地方我都在源码里加了 `【NPU 迁移提示】`。把这些提示汇总起来，就是要找华为对接的 API 清单（见第 4 节）。一键运行/诊断脚本是 `run_snvme_smoke.sh`（含大量 CUDA 初始化失败的事后诊断逻辑，迁到 NPU 后这部分诊断需重写为 NPU 版）。

## 3. 迁移到华为 NPU 910C 的详细可行计划（新手友好版）

总思路（来自 0602 分析，本文细化为可执行步骤）：**把问题拆成两条独立的线，分别验证，避免在一个巨型改动里同时排查内核版本、PCIe、NPU runtime 和 AIV：**

- **线 A：Linux 内核版本迁移线**——SNVMe 能否在华为内核上编译、加载、绑定 NVMe、跑通**纯 CPU** 队列和 BAR0 映射。**这条线不需要华为开放任何新能力，我们自己就能推进。**
- **线 B：NVIDIA GPUDirect 替换线**——华为驱动/CANN/AIV 能否提供「NVMe 直接 DMA 到 NPU 内存」和「AIV 直接敲 NVMe doorbell」。**这条线必须和华为对接。**

下面用「能力阶梯」串起来，每一级都对应一个**已有的测试程序**作为验收工具。

### 阶段 0：采集 NPU 服务器基线（线 A，必做的第一步）

登录 NPU 服务器，先把环境摸清楚（不摸清就动手是新手最容易翻车的地方）：
```bash
mkdir -p /tmp/geminifs-910c-check && cd /tmp/geminifs-910c-check
uname -a            > uname.txt          # 完整内核信息
uname -r            > uname-r.txt        # 内核版本号（决定要不要新增 baseline）
uname -m            > arch.txt           # x86_64 还是 aarch64（鲲鹏很可能是 aarch64！）
cat /etc/os-release > os.txt             # 是否 openEuler 22.03 LTS
ls -l /lib/modules/$(uname -r)/build     # 有没有内核头/构建目录（编译 .ko 必需）
grep -E 'CONFIG_MODULE_SIG|CONFIG_IOMMU|CONFIG_SMMU|CONFIG_VFIO' /boot/config-$(uname -r) > kconfig.txt
lspci -Dnn          > lspci.txt
lspci -Dnn | grep -i -E 'non-volatile|nvme' > nvme-bdf.txt   # 记下 NVMe 的 BDF
lspci -tv           > lspci-tree.txt      # NVMe 和 NPU 在不在同一个 PCIe Switch 下
lsmod               > lsmod.txt
npu-smi info        > npu-smi.txt 2>&1    # 昇腾 NPU 状态
```
**重点判断**：
1. `uname -m` 是不是 `aarch64`。如果是，`snvme_smoke_io.c` 里 `mmio_writel()` 的 `sfence` 这类 **x86 专有指令需要审计替换**（它已有 `#else` 分支用 `__atomic_thread_fence`，但要实测验证）。
2. `uname -r` 是否匹配仓库已有的 baseline（`snvme-5.15.0-public` / `snvme-5.4.241-1-tlinux4-0017`）。openEuler 22.03 LTS 通常是 `5.10.0-x` 内核——**不匹配，需要新增 baseline**（见阶段 2）。
3. 模块签名（`CONFIG_MODULE_SIG_FORCE` / Secure Boot）是否会拦自编译 `.ko`（决定能不能直接 `insmod`）。
4. 是物理机/容器/虚拟机（peer DMA 和 BAR 映射通常受部署形态限制）。

### 阶段 1：在 NPU 服务器上把代码拉下来

```bash
git clone <GeminiFS 仓库地址>
cd Geminifs
git checkout <当前分支>
git rev-parse HEAD          # 记录提交号，和团队对齐版本
```
**不要**一上来跑完整 `prepare_env.sh` 或完整 CMake（顶层 CMake 会强行找 CUDA / `nv-p2p.h`，这不是第一阶段需要的）。我们只关心 `backends/local/kernel_modules/`。

同时，按你的思路，**单独 clone 一份华为内核对应的原生 NVMe 驱动源码**作为 3-way merge 的基线之一：
```bash
# openEuler 内核源码（示例，按实际版本调整）
# drivers/nvme/host/ 就是系统原生 NVMe host driver
git clone https://gitee.com/openeuler/kernel.git openeuler-kernel
cd openeuler-kernel && git checkout <对应 tag，如 openEuler-22.03-LTS>
ls drivers/nvme/host/        # core.c pci.c nvme.h ... 这就是 SNVMe fork 的「上游」
```

### 阶段 2：决定是否新增华为内核 baseline，并完成 NVMe 驱动 uplift（线 A 核心，纯靠我们自己）

SNVMe 本质是「系统原生 NVMe host driver 的 fork + 一组改造」。改造内容 PORTING.md §3 讲得很清楚，只有两类：
1. **符号改名**（机械的）：`nvme_*` → `s_nvme_*`，避免和 in-tree 驱动符号冲突。
2. **用户驱动 bring-up**（B3 queue-group 流程）：新增一套 ioctl + queue group + DMA 映射 + BAR0 mmap。

如果 `uname -r` 不匹配已有 baseline，按 PORTING.md §7 做：
```text
backends/local/kernel_modules/snvme-<华为内核版本>/      # 新建目录
```
**三方合并（3-way merge）方法**：
- A = 旧 SNVMe baseline（如 `snvme-5.15.0-public`，是「fork 后」）
- B = 旧 baseline 对应的**原生** NVMe driver（「fork 前」）
- C = 华为内核的**原生** NVMe driver（新目标的「fork 前」）
- 目标 = 把 A 相对 B 的改动，重新应用到 C 上，得到「华为内核版的 SNVMe」。

PORTING.md §7 把这事拆成 4 个阶段，**新手务必照做、别跳**：
- §7.1 机械 merge（diff 能帮你的部分）；
- §7.2 结构性手术（diff 帮不了：probe 流程、MSI-X 分配、reset/remove 路径、命名）；
- §7.3 **语义审计**（bug 真正藏的地方：`nvme_probe`、`nvme_setup_io_queues`、锁顺序、设备命名、§7.3.1 的若干「坑」）；
- §7.4 **验证门（强制）**——就是用本文第 2 节那 6 个测试来验收。
- 全程**保持 `libnvm/include/ioctl.h` 的 UAPI 不变**（这是内核和用户态的契约）。

> 关键认知：`snvme-5.15.0-public` 是**参考实现**，不代表任意 5.15.x 厂商内核能直接用；华为的 backport 会改 NVMe/内核 API。所以哪怕版本号接近也要做语义审计。

### 阶段 3：让模块能在 host-only 模式下加载（线 A 的第一个代码改动，关键解锁点）

当前 `snvme.ko` 初始化强制 `nvfs_nvidia_p2p_init()`，找不到 NVIDIA 符号就 `-EOPNOTSUPP` 直接失败。**这是 NPU 服务器上的第一个拦路虎。**

**最小改动**：把 accelerator P2P backend 抽象化，允许「host-only」模式加载——NPU 内存相关的 ioctl（`NVM_MAP_DEVICE_MEMORY`）明确返回 `-EOPNOTSUPP`，但**所有 host 内存路径照常工作**。建议的抽象（来自 0602 §9）：
```text
snvme_accel_backend { init/exit, get_pages/put_pages, dma_map/unmap_pages,
                      free_dma_mapping/free_page_table, page_size, invalidation_cb }
实现：backend_nvidia / backend_ascend / backend_host_only
```
改完后模块能加载、`/dev/snvm_control` 出现，就可以进入阶段 4。

### 阶段 4：跑通纯 CPU 能力阶梯（线 A 验收，**不需要华为开放任何东西**）

在一块**可清空的测试盘**上，**按这个顺序**跑（先安全后破坏性）：
```bash
cd backends/local/kernel_modules/test
make            # host-only 阶段没有 nvcc 也没关系，会自动跳过 gpu 版

# 第 1 级：基础 API（安全）
sudo ./snvme_smoke_qgroup 0000:08:00.0     # 队列组生命周期，不 bind
sudo ./snvme_smoke        0000:08:00.0     # UAPI + BAR0 + host map，不 bind

# 第 2 级：注册 I/O queue（破坏性：bind）
sudo ./snvme_smoke_recycle 0000:08:00.0    # admin 透传
sudo ./snvme_smoke_addq    0000:08:00.0    # host SQ/CQ 注册成 I/O queue

# 第 3 级：CPU 全程真实读写（破坏性：写盘）—— 这一级过了 = SNVMe 内核侧在新内核上完全可用
sudo ./snvme_smoke_io      0000:08:00.0
```
**验收门槛 M1（达成即「线 A 成功一半」）**：
- `/dev/snvm_control`、`/dev/ssnvme<N>` 正常；
- `snvme_smoke`、`snvme_smoke_qgroup` 通过；
- `snvme_smoke_addq`、`snvme_smoke_recycle`、`snvme_smoke_io` 在测试盘通过。

每跑一个测试，对照第 2 节看「最后停在哪一步」，结合 `dmesg diff` 定位。**到这一步为止，你完全靠自己就能推进，不依赖华为。**

### 阶段 5：把数据缓冲换成 NPU HBM（线 B 第一步，对应你的能力阶梯第 4 步）

**目标**：SQ/CQ 和 doorbell 仍由 CPU/host 管，**只把 data buffer 换成 NPU 显存（HBM）**，验证 NVMe 能直接 DMA 读写 NPU 内存。

这一步需要华为提供「把一段 NPU 设备虚拟地址 pin 住并导出成 NVMe 可见 DMA 地址」的内核接口（语义对标 NVIDIA 的 `nvidia_p2p_get_pages` + `nvidia_p2p_dma_map_pages`）。建议**先让华为给一个最小 probe 内核模块/ioctl**，别直接塞进完整 SNVMe。验证通过后，把它实现成 `backend_ascend` 接入 `snvme-*/map.c`。

**验证工具**：把 `snvme_smoke_io.c` 复制一份改造——只把 `wbuf/rbuf`（数据缓冲）从 `posix_memalign` 换成 NPU HBM 分配 + 新的 `NVM_MAP_DEVICE_MEMORY`（Ascend backend），**SQ/CQ 环和 doorbell 保持 host 不变**。这就是 `snvme_smoke_io` 和 `snvme_smoke_gpu` 之间「缺失的中间台阶」，需要我们自己写（GPU 版的 `pdata` 持久化数据缓冲模式可直接照搬）。

### 阶段 6：把 SQ/CQ 环也换成 NPU HBM（线 B 第二步，能力阶梯第 5 步）

**目标**：SQ/CQ 环也放进 NPU HBM，但 **doorbell 仍由 CPU 代敲**。验证控制器能从 NPU 内存里读 SQE、往 NPU 内存里写 CQE。
**验证工具**：在阶段 5 的改造版上，再把 `sq_buf/cq_buf` 也换成 HBM + `NVM_MAP_DEVICE_MEMORY`，doorbell 写仍走 CPU 的 `mmio_writel`。

### 阶段 7：AIV 直接敲 doorbell（线 B 第三步，能力阶梯第 6 步，最难）

**目标**：BAR0/MMIO 映射给 NPU kernel，让 **AIV 核自己写 doorbell**。这是和华为对接的最硬骨头。最小验证程序（对标 `snvme_smoke_gpu` 的 doorbell 路径）：
1. CPU `mmap` `/dev/ssnvme<N>` 的 BAR0；
2. 用华为 runtime/驱动接口把该 MMIO 区映射成 AIV 可访问地址（对标 `cudaHostRegister(IoMemory)` + `cudaHostGetDevicePointer`）；
3. AIV 核读 CAP 或写专用测试队列的 SQ tail doorbell；
4. AIV 核执行**等价于 system-scope fence** 的指令（对标 `__threadfence_system()`）后再写 doorbell；
5. CPU 和 NVMe CQ 双侧观察结果。

若 AIV 暂不允许访问第三方 PCIe MMIO，可保留「CPU doorbell 代理」作为**功能降级**路径（能验证功能，但达不到原始 direct-IO 的性能目标）。

### 阶段 8：跑通 NPU 版 `snvme_smoke_gpu` 等价物 + 完整 GeminiFS

把阶段 5/6/7 的能力合并，写出 `snvme_smoke_npu`（对标 `snvme_smoke_gpu`，含 `--rounds` 动态分配/释放循环验证泄漏）。全绿后，再迁移 libnvm Ascend backend → NVMeService → libgeminifs → 完整 workload（这是**第二阶段**的事，本次不展开）。

## 4. 要和华为 AIV/驱动团队对接的能力清单（线 B）

这张表直接来自 0602 §6，迁移时当 checklist 用。每一项要华为明确：是否支持 910C、适用服务器形态、公开/内部/需新增 API、头文件与版本、最小 demo、权限/签名/IOMMU/拓扑约束、错误码与日志。

| 编号 | 需要的能力 | GeminiFS 用途 | 对标 NVIDIA | 缺失后果 | 对应测试阶段 |
|---|---|---|---|---|---|
| A1 | pin/export 一段 NPU 设备虚拟地址的物理页/IOVA | 导出 SQ/CQ 和数据缓冲 | `nvidia_p2p_get_pages` | NVMe 无法 DMA 到 NPU 内存 | 阶段 5/6 |
| A2 | 针对指定 NVMe `pci_dev` 建 peer DMA mapping | 拿到 NVMe 可用 DMA 地址 | `nvidia_p2p_dma_map_pages` | PRP/SGL 填不了 | 阶段 5/6 |
| A3 | unmap/put_pages/free mapping/free page table | group 销毁与异常清理 | `nvidia_p2p_put_pages` 等 | 泄漏、卸载失败 | 阶段 5/6 |
| A4 | NPU 内存失效回调 | 处理进程退出/free/reset | p2p invalidation cb | use-after-free | 阶段 5/6 |
| A5 | 返回 page size/页数/DMA 地址数组/连续性 | 正确构造 PRP/SGL | p2p page table | 跨页 IO 错 | 阶段 5/6 |
| A6 | 把第三方 NVMe BAR0 MMIO 映射成 AIV 可见地址 | AIV 直接敲 doorbell | `cudaHostRegister(IoMemory)`+`GetDevicePointer` | 只能 CPU 代理 | 阶段 7 |
| A7 | AIV 对该 MMIO 做 32-bit load/store | 更新 SQ tail / CQ head | GPU 上 `*db = val` | doorbell 敲不响 | 阶段 7 |
| A8 | AIV system-scope memory fence | 保证先写 SQE 再写 doorbell | `__threadfence_system()` | NVMe 读到半成品 SQE | 阶段 7 |
| A9 | cache flush/invalidate 或一致性规则 | CQ polling、数据可见性 | GPU coherence | CQE/数据不可见 | 阶段 7 |
| A10 | NVMe reset / NPU reset / 进程 kill 后资源回收语义 | 稳定运行与故障恢复 | — | 第二轮/复位后失败 | 阶段 8 |
| A11 | 物理机/容器/虚拟机/SMMU 限制 | 明确部署边界 | — | 实验机过、部署挂 | 全程 |
| A12 | `.ko` 编译、符号导出与签名流程 | 加载适配模块 | — | 代码完成但部署不了 | 阶段 2/3 |

**给华为的 8 个关键问题**（同 0602 §6）：910C 能否让第三方 PCIe NVMe 直接 DMA 读写 NPU HBM？有没有类 `nvidia_p2p_*` 的可被外部 `.ko` 调用的内核接口？它返回物理地址/IOVA/peer DMA 地址？经 SMMU 如何建映射？AIV 能否访问第三方 PCIe BAR MMIO、如何注册？哪条 fence 能保证 global-memory 写先于 MMIO doorbell 写对 peer 可见？NPU free/进程退出/reset 时谁负责释放 peer mapping？推荐 PCIe 拓扑（NVMe 与 NPU 是否须同 Switch）？开发/生产环境的 unsigned `.ko` 加载与签名策略？

## 5. 故障定位速查表（跑测试断在哪一步 → 看哪里 → 谁的责任）

| 失败现象 | 首要检查 | 责任边界 |
|---|---|---|
| 编译 SNVMe 失败 | `uname -r`、内核 headers、厂商 backport、baseline 是否匹配 | 线 A（内核 baseline） |
| `insmod snvme.ko` 报找不到 `nvidia_p2p_*` | 需要 host-only / Ascend backend（阶段 3） | 线 A（accelerator backend） |
| `insmod` 报 `Required key not available` | `CONFIG_MODULE_SIG_FORCE`、Secure Boot、华为签名 | 服务器内核策略（A12） |
| `/dev/snvm_control` 不出现 | 模块 init 日志、字符设备注册、符号加载 | 线 A 基础模块 |
| `SNVM_DEVICE_BIND` 失败 | NVMe BDF、原驱动是否解绑、udev autoprobe、`dmesg` | 线 A（PCI bind） |
| `snvme_smoke_io` CPU 路径失败 | host page pin、BAR0 mmap、MSI-X、B3 queue group、sfence/fence 移植 | 线 A core（阶段 4） |
| NPU 内存 pin/export 失败 | 分配方式、页对齐、华为驱动 API、权限 | 线 B 华为 runtime（A1/A5） |
| NPU 页可导出但 DMA map 失败 | NVMe peer BDF、IOMMU/SMMU、PCIe ACS、拓扑 | 线 B 华为平台（A2/A11） |
| CPU doorbell 可用，AIV doorbell 不可用 | BAR0 注册、AIV MMIO 权限、地址转换 | 线 B 华为 AIV（A6/A7） |
| AIV 能敲 doorbell 但 IO 超时/数据错 | fence、cache 一致性、PRP/SGL、page size | 线 B AIV 语义（A8/A9） |
| 第一轮过、第二轮失败 | unmap、失效回调、queue delete、QID 回收（`--rounds` 能复现） | cleanup/reset 语义（A10） |

## 7.【动手指南】先迁 B3 模块到 openEuler 的完整步骤（本次选定路线）

> 这一节回答你的三个具体问题：**(1) 是不是要自己一点点手敲代码？(2) clone 后机器上有 openEuler 原生 nvme/host，是不是要先改它编译出 .ko？(3) B0 和 B3 差这么多，先改哪些文件、要不要编译、怎么测？**
> 路线已选定：**先把 B3 模块（`Geminifs_smoke` 里的 `snvme-5.15.0-public`）迁到 openEuler，让 6 个测试直接可用，先证明「平台+内核+NPU 能力到底行不行」，B0 产品之后再单独处理。**

### 8.1 先认清你机器上的三个目录（别搞混）

NPU 服务器上 clone 完，和这三个目录打交道：

| 目录 | 是什么 | 你对它做什么 |
|---|---|---|
| `Geminifs/module/` | **B0** 模块（要迁移的旧产品，无测试） | 本路线**暂时不动**，第二阶段再处理 |
| `Geminifs_smoke/backends/local/kernel_modules/snvme-5.15.0-public/` | **B3** 模块（新版，配套 6 个测试） | **本路线的主角**，要把它迁到 openEuler |
| `kernel-openEuler-22.03-LTS-drivers-nvme/drivers/nvme/host/` | openEuler **原生** NVMe 驱动 | 只当**三方合并的参照**，**不在原地改它、不重编内核** |

**关键心智模型（最容易误解的地方）**：

```
   旧 SNVMe 基线(B3)          原生 Linux 5.15 的 nvme/host        openEuler 5.10 的 nvme/host
   snvme-5.15.0-public   ─┐   (三方合并的「base/基」)        ─┐   (三方合并的「右/新上游」)
   (三方合并的「左/改后」) │                                  │
                          └──────────► 三方合并(3-way merge) ◄──┘
                                            │
                                            ▼
                            新基线目录  snvme-5.10-openeuler/   ← 你产出的东西
                                            │  make（树外编译）
                                            ▼
                            snvme-core.ko + snvme.ko            ← 两个内核模块
                                            │  insmod
                                            ▼
                            /dev/snvm_control 出现 → 跑 test/ 里的 6 个测试
```

- **你不是在改 openEuler 内核源码树、也不是重编整个内核。** SNVMe 是**树外模块（out-of-tree module）**：从它自己的目录用 `make -C /lib/modules/$(uname -r)/build M=...` 编出 `.ko`，对着「正在运行的内核的头文件」编译即可。
- openEuler 的 `drivers/nvme/host` 只是参照：因为 SNVMe 本质是「某个版本 Linux 原生 nvme 驱动的 fork + 改造」，换内核版本时要把改造**重新套用**到 openEuler 这版原生驱动上。
- 原生 `nvme.ko` 继续加载、继续管别的盘；SNVMe 靠**符号改名**和它共存。

### 8.2 你到底要不要「手敲代码」？——大部分是合并，不是手写

把 B3 模块的 24 个文件分成两类（已实测分类）：

**第一类：13 个 SNVMe 新增文件**（openEuler 原生 nvme/host 里根本没有）——**几乎原样搬过去**，只跟着改名、跟着调内核 API：
```
ctrl.c  ctrl.h  ioctl.c  list.c  list.h  map.c  map.h
nvfs-core.h  nvfs-p2p.c  nvfs-p2p.h  nvfs-pci.c  nvfs-pci.h  Makefile.in
```
> 这些是 SNVMe 的「附加功能层」（字符设备、ioctl、queue group、DMA 映射、NVIDIA p2p 胶水）。它们不在原生驱动里，所以**不需要合并**，直接拷进新基线目录，编译时按报错修内核 API 即可。

**第二类：11 个改自原生的文件**——需要**三方合并**：
```
core.c   pci.c   nvme.h        ← 真正要动手术的（SNVMe 改造集中在这几个，尤其 pci.c）
fabrics.c  fabrics.h  hwmon.c  multipath.c  rdma.c  tcp.c  zns.c   ← 基本只是机械改名
```
> 「手敲」的真实含义：
> - **改名**（`nvme_*` → `s_nvme_*` 等）：**机械、可自动化**，仓库里有 `snvme-rename.sed` 这类脚本。
> - **三方合并**：用 `git merge-file` / `meld` / `kdiff3` 把「B3 相对原生 5.15 的改动」重新套到 openEuler 5.10 原生上，**冲突逐处解决**。这是体力活但不是从零手写。
> - **真正手写的只有一处且很小**：第 8.4 步的「host-only / Ascend backend 抽象」——让模块在没有 NVIDIA 时也能加载。这部分是新代码，但隔离在 `nvfs-p2p.c` 一带。
>
> 结论：**90% 是「改名 + 合并 + 按编译报错修 API」，约 10% 是新写一小块 backend 抽象。不存在「把 24 个文件从头手敲一遍」。**

### 8.3 先改哪个文件？——优先级顺序

按「先让它能编译加载，再让它功能正确」的顺序：

| 优先级 | 文件 | 做什么 | 为什么先做它 |
|---|---|---|---|
| ① | 全部文件的**符号改名** | 跑 `snvme-rename.sed`（需按 5.10 重新核对一遍导出符号） | 不改名两个模块会「重复导出符号」加载失败 |
| ② | `nvme.h` | 三方合并结构体/宏；SNVMe 往 `struct nvme_dev` 注入的字段要保留 | 它是 core.c/pci.c 的公共头，先稳定它 |
| ③ | `pci.c` | **重头戏**：probe 流程、MSI-X 分配、`use_sreg` 分支、BAR0 mmap、queue group 接入。三方合并 + 语义审计 | SNVMe 改动最集中（B3 的 pci.c 比原生大 +93KB） |
| ④ | `core.c` | 三方合并；admin queue、reset/remove、设备命名（`/dev/snvmeXnY`） | 与 pci.c 强耦合 |
| ⑤ | `ioctl.c` / `map.c` / `ctrl.c` / `list.c` | 直接拷入，按编译报错修内核 API（如 `get_user_pages_fast` 签名、`blk_mq` 接口变化） | 是新增层，依赖 ②③④ 的符号 |
| ⑥ | `nvfs-p2p.c` | 加 **host-only 开关**（见 8.4），让没有 NVIDIA 时也能加载 | 这是 NPU 服务器能加载的前提 |
| ⑦ | `fabrics/hwmon/multipath/rdma/tcp/zns` | 只改名，编不过再修 | 改动最少，放最后 |

> PORTING.md §7 把合并拆成 4 个阶段（机械合并 → 结构性手术 → **语义审计** → 验证门），强烈建议照它做，尤其 §7.3 的语义审计是 bug 真正藏的地方。

### 8.4 完整动手步骤（从 0 到跑通 6 个测试）

**Step 0 — 确认内核版本，建新基线目录**
```bash
uname -r            # 例如 5.10.0-60.18.0.50.oe2203.aarch64 → openEuler 22.03 LTS 是 5.10
cd Geminifs_smoke/backends/local/kernel_modules
cp -r snvme-5.15.0-public snvme-5.10-openeuler   # 以 B3 的 5.15 基线为起点
```
> 仓库已有 5.15 和 5.4 两个基线，**都不匹配 5.10**，所以必须新建 `snvme-5.10-openeuler/`。

**Step 1 — 准备三方合并的三份源码**
```text
左(改后)  = snvme-5.15.0-public/              （仓库已有）
基(原生)  = 原生 Linux v5.15 的 drivers/nvme/host  （需 git clone linux 后 checkout v5.15 拿到）
右(新上游)= kernel-openEuler-22.03-LTS-drivers-nvme/drivers/nvme/host/  （机器上已有）
```
做法：先算出「左 相对 基」的改动 = **SNVMe 补丁**，再把这个补丁套到「右」上、逐处解冲突。逐文件可用：
```bash
# 对每个「第二类」文件，例如 pci.c：
git merge-file -p \
  kernel-openEuler-.../host/pci.c \   # 右（新上游，作为输出基础）
  <原生5.15>/pci.c \                  # 基
  snvme-5.15.0-public/pci.c \         # 左（带 SNVMe 改造）
  > snvme-5.10-openeuler/pci.c        # 输出，手动解 <<<< ==== >>>> 冲突
```
**第一类的 13 个新增文件直接 `cp` 进 `snvme-5.10-openeuler/`，不参与合并。**

**Step 2 — 机械改名**
```bash
# 按 5.10 实际导出符号核对后，对新基线所有 .c/.h 跑改名脚本
cd snvme-5.10-openeuler
sed -i -f ../snvme-5.4.241-1-tlinux4-0017/snvme-rename.sed *.c *.h   # 注意：5.10 的导出符号要重新核对，不能照搬 5.4 的清单
```

**Step 3 — host-only 改动（关键解锁点，唯一要"新写"的一小块）**
打开 `nvfs-p2p.c`，把模块初始化里强制 `nvfs_nvidia_p2p_init()`（找不到 `nvidia_p2p_*` 就 `-EOPNOTSUPP`）改成**可选**：找不到就进入 host-only 模式，让所有 host 内存路径照常工作，NPU 内存 ioctl（`NVM_MAP_DEVICE_MEMORY`）明确返回 `-EOPNOTSUPP`。这样在没有 NVIDIA 的 NPU 服务器上模块也能加载。

**Step 4 — 编译出 .ko（树外编译，不重编内核）**
```bash
# 准备内核头：openEuler 上装 kernel-devel/kernel-headers，确认存在
ls /lib/modules/$(uname -r)/build      # 必须存在，否则装 kernel-devel
# Makefile.in 里 @module_root@ 等占位符由顶层 CMake 渲染；不想用 CMake 可手写一个 Makefile：
#   obj-m += snvme-core.o snvme.o
#   snvme-core-y := core.o ioctl.o multipath.o zns.o hwmon.o
#   snvme-objs   := nvfs-pci.o nvfs-p2p.o list.o ctrl.o map.o pci.o
#   all: ; make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
make -C /lib/modules/$(uname -r)/build M=$(pwd) modules
ls -l snvme-core.ko snvme.ko           # 编出来这两个就成功
```
> 编译报错基本都是「内核 API 在 5.10 和 5.15 之间变了」——逐个查 5.10 内核头改签名即可（这是迁移最耗时但最确定的体力活）。

**Step 5 — 加载模块**
```bash
# 若 uname -m 是 aarch64：先确认 snvme_smoke_io.c 的 mmio_writel sfence 分支（x86 专有）
#   已走 #else 的 __atomic_thread_fence，编译没问题，但要实测排序语义。
sudo insmod snvme-core.ko
sudo insmod snvme.ko
ls -l /dev/snvm_control                 # 出现（mode 0666）= 加载成功
dmesg -T | tail -40                     # 看 init 日志；host-only 模式应有相应提示
```
> 若卡在「Required key not available」= 内核开了 `CONFIG_MODULE_SIG_FORCE`，需要签名或换一台没开强制签名的开发机（PORTING.md §6.1）。

**Step 6 — 按顺序跑 6 个测试（先安全后破坏性）**
```bash
cd ../test
make                                    # 没 nvcc 会自动跳过 gpu 版
BDF=$(lspci -D -d ::0108 | awk 'NR==1{print $1}')   # 自动取第一个 NVMe，或手填

# 第 1 级（安全，不 bind）
sudo ./snvme_smoke_qgroup $BDF
sudo ./snvme_smoke        $BDF
# 第 2 级（破坏性：bind，用可清空的测试盘）
sudo ./snvme_smoke_recycle $BDF
sudo ./snvme_smoke_addq    $BDF
# 第 3 级（破坏性：写盘）
sudo ./snvme_smoke_io      $BDF
# 也可用一键脚本（含环境诊断）
sudo ./run_snvme_smoke.sh  $BDF
```
**判读**：每个测试成功末尾打印 `all N steps passed`；失败时**最后一行 `[FAIL] step=N`** 就是断点，对照第 2 节的步骤表 + `dmesg diff` 定位。跑到这里全绿 = **达成 M1（纯 CPU 能力阶梯通过，平台+内核 OK）**。

**Step 7 — 之后才是 NPU 相关（线 B）**
M1 通过后，再按第 3 节阶段 5~8 接华为 NPU 能力：先把数据缓冲换 NPU HBM（需华为 peer DMA 接口，对标 `nvidia_p2p_*`），再换队列环，最后让 AIV 自己敲 doorbell，最终跑通对标 `snvme_smoke_gpu` 的 NPU 版。这部分必须按第 4 节清单和华为对接。

### 8.5 B0 产品怎么办（本路线下的后续）

先迁 B3 跑通测试，等于先确认了「这台 NPU 服务器 + 这个内核 + 这块 NVMe」整条直连通路是否可行。之后处理 B0 有两个选择，到时再定：
- **若 B3 在 openEuler 上稳定**：评估能否让产品直接采用 B3（B3 的 UAPI 是 B0 的超集，功能更全），省掉单独迁 B0。
- **若必须保留 B0**：把同一套 openEuler 适配（改名 + 三方合并 + host-only）重新套到 `Geminifs/module/`（B0）上。B0 没有 queue-group，所以它的测试只能覆盖到「host SQ/CQ + CPU IO」的旧流程，需要按 B0 的 UAPI 单独写几个简化测试（参考 `snvme_smoke` 的 `[1]~[9]`，但把 `NVM_SET_IOQ_NUM` 的入参换回 B0 的 `struct nvm_ioctl_dev`）。

> 注：仓库里 `Geminifs/ascend_cann_port/` 是**用户态** CANN 移植工作区（host 端 AscendCL + Ascend C kernel，明确不碰 `module/`），和本文的内核模块迁移是**两条并行线**，互不冲突。本文只管内核模块（kernel_modules）这条线。

## 8. 一句话总结

**先用「能力阶梯」把迁移拆成 6 级，每一级都有一个现成的 smoke 测试做验收**：第 1~3 级（`qgroup/smoke/recycle/addq/io`）是**纯 CPU、纯内核版本迁移**，我们自己就能推到 M1；第 4~6 级（数据缓冲→队列环→doorbell 逐步搬上 NPU，最终对标 `snvme_smoke_gpu`）需要华为按第 4 节清单逐项开放能力。断在哪一级，就照第 5 节定位表判断是「我们的内核移植问题」还是「华为的 NPU 能力缺口」，从而高效对接。

**本次选定的落地路线（见第 7 节）**：先把 **B3 模块**（不是 B0）迁到 openEuler——因为只有 B3 配套那 6 个测试，迁过去就能直接验证「平台+内核+NPU 到底行不行」。迁移的 90% 是「符号改名 + 三方合并 + 按编译报错修内核 API」，不是从零手敲；真正新写的只有一小块 host-only/Ascend backend 抽象。B0 产品等 B3 跑通后再单独处理。
